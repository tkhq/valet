# Findings: pi-agent-core continuation spike

Run: 2026-07-11, pi-agent-core 0.73.0 / pi-ai 0.73.0, models `claude-haiku-4-5` (primary), `claude-sonnet-4-5` (thinking leg), `gpt-4o-mini` (cross-provider leg, auth failed — see Scenario E). No model id substitutions were needed; all three ids resolved directly from pi-ai's registry (`getModel` did not throw).
Script: `experiments/continuation-spike.ts` (rerunnable; requires `ANTHROPIC_API_KEY` from repo `.env`; `OPENAI_API_KEY` is optional and, in this environment, a placeholder value rather than a live key).

## Verdict for Phase 1

The rehydrate → fabricate `ToolResultMessage` → `runAgentLoopContinue` design is viable as specced. A `[user, assistant]` pair JSON round-tripped through a temp file (simulating text-column SQLite persistence), with a hand-built `ToolResultMessage` appended for the dangling `toolCallId`, is accepted by `runAgentLoopContinue` and produces a completed turn (`stopReason: "stop"`) whose response text demonstrably reflects the injected value rather than a re-derived one — and no tool re-execution occurred (`tool_execution_start` never fired). This held for both a single dangling call (B) and two parallel dangling calls in one assistant message (C), confirming multi-`tool_result` ordering is not a blocker. No contract adjustments to the core design are required for the happy path. Two adjustments Phase 1 should still make going in: (1) treat model-switch-mid-turn as provisionally safe per this spike but re-verify at Phase 1 time since Anthropic's acceptance of "foreign" thinking signatures across models is not a documented guarantee and could change; (2) Scenario E did not actually exercise cross-provider tool-call-id handling because the available `OPENAI_API_KEY` was a placeholder — this leg is unverified, not passing, and should be re-run with a real key before Phase 1 relies on any anthropic→openai handoff behavior.

## Rules Phase 1 must adopt

- `convertToLlm` must guarantee the trailing message is `user`/`toolResult` before calling `agentLoopContinue` — `runAgentLoopContinue`'s own type contract says the provider will reject the request otherwise. This spike's `loopConfig.convertToLlm` filters to `user | assistant | toolResult` roles but relies on the caller to have appended the fabricated `ToolResultMessage` as the last message; Phase 1's production rehydration path must enforce this ordering explicitly (e.g. an assertion) since silent violation would surface only as an opaque provider 400.
- Fabricated `ToolResultMessage`s must carry the correct `toolCallId` (and, per pi-ai's `ToolResultMessage` shape, `toolName`) pulled from the persisted assistant message's `toolCall` content block — not reconstructed from any other source. The spike's `fabricatedResult()` helper does this by reading `call.id`/`call.name` straight off the rehydrated assistant message; Phase 1's SQLite rehydration should follow the same pattern (id sourced from the persisted tool_call, not recomputed).
- Do not assume Scenario E's result generalizes — Phase 1 should not build cross-provider mid-turn failover logic on an untested assumption. Re-run Scenario E with a real `OPENAI_API_KEY` before committing to any anthropic→openai (or other cross-provider) continuation behavior in the design.

## Surprises / gotchas

- Both C (parallel tool calls) and D (thinking-model tool call) succeeded in eliciting the intended shape on the *first* attempt — no retries were needed, contrary to the brief's expectation that C might need up to 3 attempts.
- Scenario D's cross-model continuation (sonnet-with-thinking → haiku) succeeded without stripping the thinking block, which was not the expected/cautious outcome going in. This is a favorable result but should be treated as one data point, not a guarantee — Anthropic's handling of foreign thinking signatures across model families isn't publicly documented as stable, and Phase 1 should keep the "strip thinking on model switch" code path available as a fallback even though this spike didn't need it.
- The repo's `.env` `OPENAI_API_KEY` is a placeholder (`your-ope***-key` per the API's own error echo), which means Scenario E could not test what it was designed to test. This should be flagged to whoever owns Phase 1 credentials before that scenario is relied upon.
- `runAgentLoopContinue`'s `tool_execution_start` event is a reliable signal for "the loop tried to actually run the tool" — used here as the `!toolExecuted` assertion in B/C to prove the fabricated result short-circuited re-execution. Confirmed working as documented.
