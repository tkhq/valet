# Findings: pi-agent-core continuation spike

Run: 2026-07-11 (four full runs), pi-agent-core 0.73.0 / pi-ai 0.73.0, models `claude-haiku-4-5` (primary), `claude-sonnet-4-5` (thinking leg), `gpt-4o-mini` (cross-provider leg). No model id substitutions were needed; all three ids resolved directly from pi-ai's registry (`getModel` did not throw). Run history: runs 1–2 had no valid `OPENAI_API_KEY` (E blocked at auth); run 3 (valid key, B2 scenario added by then) hit a transient OpenAI server error on E; run 4 completed E successfully. A–D (and B2 from run 3 onward) were identical across all runs — no nondeterminism observed.
Script: `experiments/continuation-spike.ts` (rerunnable; requires `ANTHROPIC_API_KEY` and, for Scenario E, a valid `OPENAI_API_KEY`, both from repo `.env`).

## Verdict for Phase 1

The rehydrate → fabricate `ToolResultMessage` → `runAgentLoopContinue` design is viable as specced. A `[user, assistant]` pair JSON round-tripped through a temp file (simulating text-column SQLite persistence), with a hand-built `ToolResultMessage` appended for the dangling `toolCallId`, is accepted by `runAgentLoopContinue` and produces a completed turn (`stopReason: "stop"`) whose response text includes the injected value — and no tool re-execution occurred (`tool_execution_start` never fired) — for both a single dangling call (B) and two parallel dangling calls in one assistant message (C), confirming multi-`tool_result` ordering is not a blocker.

**What B alone does NOT prove, and what B2 adds:** Scenario B's arithmetic (7 × 6) is verifiable, and the fabricated result ("42") happens to equal the correct answer, so `text.includes("42")` cannot distinguish "the model read the injected tool result" from "the model silently recomputed 7×6 itself and got the same number." Scenario B2 closes that gap by rerunning the identical setup with a *deliberately wrong* fabricated result ("99" for 7×6). The outcome: the model did **not** adopt 99 — it replied `"The result of 7 * 6 is **42**."`, i.e. it recomputed/asserted the correct answer and ignored (or overrode) the injected tool result. `reExecutedTool` was still `false` (no `tool_execution_start` fired), so the override happened via the model's own reasoning over the text content, not by re-invoking the tool.

Combined, B + B2 establish: the mechanism (rehydrate → fabricate → continue) is structurally accepted by `runAgentLoopContinue` with no wiring errors, and the model does not re-execute the tool. They do **not** establish that the model faithfully "consumes" an injected result as ground truth — for at least one verifiable-arithmetic case, the model overrode a contradictory fabricated value with its own computation while still reporting `stopReason: "stop"` as if the turn completed normally. Phase 1 cannot assume fabricated tool results are treated as authoritative; see "Rules Phase 1 must adopt" below.

Two further adjustments Phase 1 should make going in: (1) treat model-switch-mid-turn as provisionally safe per this spike but re-verify at Phase 1 time since Anthropic's acceptance of "foreign" thinking signatures across models is not a documented guarantee and could change; (2) cross-provider handoff (Scenario E) now has a real positive observation — OpenAI's Responses API accepted the Anthropic transcript with its raw `toolu_…` tool-call id passed straight through as `call_id`, and the continuation completed with `stopReason: "stop"` and the fabricated "42" reflected in the answer — but the successful run was preceded by a transient OpenAI server error (`An error occurred while processing your request … req_2e9845759fa9485cb939f3b58317f0a6`) on an identical request, so Phase 1's cross-provider path must treat provider 5xx-style errors as retryable rather than as evidence of transcript-shape incompatibility.

## Rules Phase 1 must adopt

- `convertToLlm` must guarantee the trailing message is `user`/`toolResult` before calling `agentLoopContinue` — `runAgentLoopContinue`'s own type contract says the provider will reject the request otherwise. This spike's `loopConfig.convertToLlm` filters to `user | assistant | toolResult` roles but relies on the caller to have appended the fabricated `ToolResultMessage` as the last message; Phase 1's production rehydration path must enforce this ordering explicitly (e.g. an assertion) since silent violation would surface only as an opaque provider 400.
- Fabricated `ToolResultMessage`s must carry the correct `toolCallId` (and, per pi-ai's `ToolResultMessage` shape, `toolName`) pulled from the persisted assistant message's `toolCall` content block — not reconstructed from any other source. The spike's `fabricatedResult()` helper does this by reading `call.id`/`call.name` straight off the rehydrated assistant message; Phase 1's SQLite rehydration should follow the same pattern (id sourced from the persisted tool_call, not recomputed).
- Cross-provider (anthropic→openai) mid-turn handoff is viable: OpenAI's Responses API accepts foreign `toolu_…` tool-call ids and pi-ai's converter handles the id mapping. But Phase 1's cross-provider path must distinguish transient provider errors from shape incompatibility — an identical request 500'd once (generic "An error occurred while processing your request" with a request ID) and succeeded on retry. Treat `stopReason: "error"` with a non-4xx/generic error body as retryable before concluding the transcript can't be handed off. Note this is one model pair (`claude-haiku-4-5` → `gpt-4o-mini`) on one API family (Responses); transcripts containing thinking blocks crossing providers were NOT tested.
- **Injecting a fabricated tool result does not guarantee the model treats it as authoritative.** Established: the mechanism is structurally accepted (`stopReason: "stop"`, no re-execution) whether the injected value is correct (B) or wrong (B2). NOT established: that the model's final answer will reflect the injected value when it conflicts with something the model can independently re-derive — in B2 the model recomputed 7×6 and reported the correct answer instead of the fabricated "99", with no error surfaced and no distinguishing signal other than the text itself disagreeing with the injected result. Phase 1 must not design around "the model will say whatever the persisted tool result says" for results the model is capable of re-checking (arithmetic, simple lookups it may have memorized, etc.). For results the model *cannot* independently re-derive (e.g. a file read, an API call, a random UUID), this spike provides no evidence either way — that case is untested and should not be assumed safe by extrapolation from B2's narrow arithmetic case. Any Phase 1 mechanism that depends on the model faithfully relaying a persisted-but-unverifiable tool result should get its own targeted spike before being relied upon.
- Provider auth/runtime failures during a continuation do not throw out of `runAgentLoopContinue`; they surface as a final `AssistantMessage` with `stopReason: "error"` and `errorMessage` set (observed twice in Scenario E). Phase 1's resume path must check `stopReason` on the continuation's final assistant message rather than relying on try/catch to detect a failed resume.

## Surprises / gotchas

- Both C (parallel tool calls) and D (thinking-model tool call) succeeded in eliciting the intended shape on the *first* attempt — no retries were needed, contrary to the brief's expectation that C might need up to 3 attempts.
- Scenario D's cross-model continuation (sonnet-with-thinking → haiku) succeeded without stripping the thinking block, which was not the expected/cautious outcome going in. This is a favorable result but should be treated as one data point, not a guarantee — Anthropic's handling of foreign thinking signatures across model families isn't publicly documented as stable, and Phase 1 should keep the "strip thinking on model switch" code path available as a fallback even though this spike didn't need it.
- Scenario E's history is a cautionary tale about credential and transient-error noise masquerading as findings: runs 1–2 failed on invalid keys (`.env` placeholder, then a revoked shell-profile key), and run 3 — first with a valid key — failed on a transient OpenAI server error that looked superficially like a rejection. Only direct API probes (curl/urllib against both Chat Completions and Responses with a hand-built `toolu_…` transcript, both 200) plus a fetch-instrumented pi-ai replay isolated the real answer: the handoff works, and the run-3 error was server-side flakiness.
- pi-ai routes `gpt-4o-mini` through OpenAI's **Responses API**, not Chat Completions — relevant for anyone debugging cross-provider requests, since the wire shape is `function_call`/`function_call_output` items, not `tool_calls`/`role:"tool"` messages.
- `runAgentLoopContinue`'s `tool_execution_start` event is a reliable signal for "the loop tried to actually run the tool" — used here as the `!toolExecuted` assertion in B/C to prove the fabricated result short-circuited re-execution. Confirmed working as documented.
