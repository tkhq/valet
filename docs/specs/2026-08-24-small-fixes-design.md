# Small Fixes Design — five independent defects from the 2026-08-24 call

**Date:** 2026-08-24
**Status:** Proposed
**Scope:** Five small defects reported on the 2026-08-24 planning call, bundled into one document because each is too small for a spec of its own. They are the events tab showing the whole org, the workspace switcher not reaching the dashboard or the memory document pane, the homepage usage card and its uncapped leaderboard, empty Slack messages on tool-only rounds, and a reported "split-brain on certain models" whose symptom was never described. The five share no code and no ordering constraint, so each ships as its own pull request. V2 stack only (`packages/api`, `packages/engine`, `packages/web`, `packages/plugin-slack`). The frozen legacy stack is not touched.

Every file and line reference below is against `dev-v2` at commit `e33701dc`, the tip that carries the artifacts and sandbox-tiering merges.

## Context

### A. The events tab shows the whole organization

`GET /api/events` filters on one column: `const conditions = [eq(events.orgId, user.orgId)]` (`packages/api/src/routes/events.ts:238`), then adds the optional `service` and `key` filters the page's two dropdowns send. `GET /api/event-subscriptions` filters on the same single column, `.where(eq(eventSubscriptions.orgId, user.orgId))` (`events.ts:480`). Every member of an organization therefore sees every colleague's automations.

The subscriptions half is deliberate and documented. Ownership is recorded on the row (`eventSubscriptions.ownerType` / `ownerId`, `packages/api/src/schema/index.ts:1497-1499`) and enforced for mutation by `canMutateSubscription` (`events.ts:56-65`), while the router docstring states that org-wide visibility is the intent: everyone can see every subscription, and the owner gate is mutation-only (`events.ts:42-49`). A route test pins it — `"lists only the caller's org's subscriptions"` seeds a second organization's row and asserts that only the caller's organization comes back (`packages/api/src/routes/events.test.ts:378-391`). This item is a reversal of a deliberate decision, not a bug fix, so the docstring and the test move with the code.

The feed half is a different shape. The `events` table has no owner column at all — it carries `orgId`, `service`, `eventKey`, `dedupeKey`, `actor`, `refs`, `summary`, `payload` and two timestamps (`schema/index.ts:1470-1490`). Ownership is one join away, through `event_deliveries.subscriptionId → event_subscriptions.ownerType/ownerId` (`schema/index.ts:1574-1592`), and `event_deliveries_event` already indexes the join column. The team workspace design records the current behavior as a decision: the feed lists organization-level facts rather than owned rows, and it stays unscoped on purpose (`docs/specs/2026-08-17-team-workspace-ui-design.md:105-106`). The feed component's own docstring gives the reason — a row expands into its delivery attempts so that "my subscription never fired" is answerable from the page (`packages/web/src/components/events/feed.tsx:20-25`), and an event that matched nothing you own is exactly the event you need to see to answer it.

Nothing on the client side carries an owner either. The page renders `<EventFeed />` and `<SubscriptionsPanel />` with no props and no workspace clause (`packages/web/src/routes/events.index.tsx:33-59`), `useEvents` takes only `service` and `key` (`packages/web/src/api/events.ts:44-52`), `useEventSubscriptions` takes no arguments (`api/events.ts:83-89`), the query keys hold no owner (`api/events.ts:26-31`), and neither `listEvents` nor `listEventSubscriptions` accepts an `OwnerFilter` (`packages/web/src/api/client.ts:699-710`).

### B. The workspace switcher does not reach three surfaces

The switcher holds a routing key and persists it to `localStorage["valet:workspace"]` (`packages/web/src/lib/workspace-scope.tsx:38`, `:105-152`). One adapter turns that key into an owner pair for a list endpoint: `useListOwner()` (`packages/web/src/lib/use-list-owner.ts:25-33`). Twelve surfaces read it, among them the sessions list, the workflows list, the memory tree and search pane, the skills catalog and the chat rail. Three do not.

**Threads.** The dashboard threads card resolves its session through `useOrchestratorInfo()` (`packages/web/src/components/assistant/threads-card.tsx:79-83`). That endpoint is hard-wired to the caller's own principal — `const principal = userPrincipal(user.id)` followed by `resolveDefaultAssistant(db, user.orgId, principal)` (`packages/api/src/routes/orchestrator.ts:109-111`) — and has no team branch. The chat rail is unaffected because it reads the scope directly (`packages/web/src/components/session/assistant-rail.tsx:95`). Only the dashboard card is pinned.

**Memories.** The tree and search pane in the left sidebar are scoped (`packages/web/src/components/memory/memory-search.tsx:48`), but clicking a row navigates to `/memory/$`, which renders `MemoryDoc`, and that component reads and writes without an owner: `useMemoryDoc(path)` (`packages/web/src/components/memory/memory-doc.tsx:52`), `api.writeMemoryDoc({ path, content })` (`:62`), the pin write (`:73`) and `api.deleteMemoryDoc(path)` (`:81`). The hooks already accept an owner and already key the cache on it (`packages/web/src/api/memory.ts:19-26`, `:47-52`); the three client methods do not accept one at all (`packages/web/src/api/client.ts:495-501`). The server is not the problem — every memory route resolves its scope from `?ownerType=&ownerId=` through `resolveScope` (`packages/api/src/routes/memory.ts:150-193`), and the write routes read the same pair as the read routes (`memory.ts:368-371`, `:487-490`). The result today is that a team-scoped tree opens personal documents, and an edit, a pin or a delete writes to the personal owner. The dashboard memory card has the same gap on its two reads (`packages/web/src/components/assistant/memory-card.tsx:54`, `:57`), and so do the export and import buttons in the memory sidebar (`packages/web/src/components/memory/import-export.tsx:109`, `:161`).

**Usage.** No layer carries a scope. The card queries on the key `["usage","summary"]` with no owner (`packages/web/src/components/assistant/usage-card.tsx:18-22`), the client method takes no parameters (`client.ts:768`), and the route reads no query parameters at all: `me` is pinned to `user.id` and the comparison block covers the whole organization (`packages/api/src/routes/usage.ts:86-92`, `:103-129`). The data supports a team scope already — the `cost_entries` view resolves `owner_type` and `owner_id` for both session-backed and workflow-backed turns (`packages/api/migrations/pg/0000_app.sql:964-996`).

### C. The homepage usage card and its uncapped leaderboard

Two separate things are wrong, and neither was reproduced against a running deployment.

The layout asymmetry is the best-supported reading of "broken". The usage card body is `<div className="px-4 py-3 space-y-3">` with no height cap and no scroller (`packages/web/src/components/assistant/usage-card.tsx:36`). It is the only one of the four dashboard cards in that state: the threads card, the memory card and the teams card all carry `overflow-y-auto max-h-64` (`threads-card.tsx:100`, `memory-card.tsx:78`, `teams-card.tsx:86`). The four sit in a two-column grid where the memory card and the usage card share a row (`packages/web/src/routes/index.tsx:74-81`), so an organization with many spenders stretches the grid row and leaves the capped memory card as a mostly empty box beside it.

Nothing bounds the member list at any layer. The aggregate SQL has no `ORDER BY` and no `LIMIT` (`usage.ts:66-83`), the route sorts the result and never truncates it (`usage.ts:117-128`), and the card renders every row (`usage-card.tsx:68`). The unbounded list also drives the second query: `spenderIds` feeds an `inArray` over every spender who has any priced or unpriced turn in the 30-day window (`usage.ts:110-118`).

Two further hazards live in the same component. `Math.max(0, ...(data?.org?.members.map((m) => m.costUsd) ?? []))` spreads the whole array into an argument list (`usage-card.tsx:25`); at a few thousand members that throws a range error and blanks the card. And when every turn in the window is unpriced, every `costUsd` is zero, `max` is zero, `fraction` is zero (`usage-card.tsx:134`) and every bar renders at the two-percent floor (`:144`) — a flat chart that contradicts the numbers beside it, which correctly render an em dash for the same rows (`windowCostDisplay`, `:104-109`).

### D. Slack posts empty messages on tool-only rounds

The engine emits `message_start` for every assistant round, not only the turn-final one (`packages/engine/src/thread.ts:3013-3046`). A round that is pure tool calls with no preamble text ends with a provider stop reason of `toolUse`, which the engine maps to `stopReason: undefined` on the persisted entry (`thread.ts:3119-3126`) while still emitting `message_end` with reason `end_turn` (`thread.ts:3148-3161`).

The stream bridge opens a Slack stream on that event unconditionally. The `message_start` branch calls `registerStream` and then fires the opener immediately: `void this.guard("open", opener)` (`packages/api/src/channels/stream-bridge.ts:295-300`). The opener calls `transport.startStream` (`stream-bridge.ts:397-403`), which reaches `chat.startStream` with no `markdown_text`, because the bridge never passes one and the field is only written when defined (`packages/plugin-slack/src/transport/transport.ts:525-531` → `packages/plugin-slack/src/transport/api.ts:182-198`). Slack mints and returns a timestamp for a message with no text.

If no `text_delta` follows, the close path finalizes that empty message. `message_end` calls `finish` with no note (`stream-bridge.ts:312-321`); `finish` appends nothing because the note is undefined (`:624-626`), the final flush returns immediately because the buffer is empty (`flushOnce`, `:486`), and `closeRef` calls `stopStream` with no tail (`:641-655` → `transport.ts:565-577` → `api.ts:208-218`). A Slack message is created and finalized with zero characters.

Because `this.pending` is cleared only on `turn_end` (`stream-bridge.ts:333-336`) while `this.active` is cleared on every `finish` (`:621`), the guard at `stream-bridge.ts:288` admits a new stream for each assistant round. A turn with several tool-calling rounds and no narration produces one empty Slack message per round, followed by the real answer. Whether a model narrates before calling tools varies by model and by prompt, which is why the report says "occasionally".

The turn-final rule that would suppress this exists, but only on the discrete path: `deliverAssistantMessage` returns early unless the persisted entry carries `stopReason === "end_turn"` (`packages/api/src/channels/host.ts:475`), and the same file's earlier guard skips any message the bridge marked as streamed (`host.ts:458`). The bridge has no access to a stop reason — the engine's `message_start` event carries only a thread id, a message id and a role (`packages/engine/src/types.ts:1133`) — so the streaming path cannot apply the same rule. The intent is nonetheless written down one function earlier in the bridge: a turn that parks on an approval gate before it writes anything must not leave an empty stream on screen (`stream-bridge.ts:236-239`). That reasoning was never applied at `message_start`.

Slack has no delete capability in this codebase — there is no `chat.delete` call anywhere in `packages/plugin-slack/src` — so an empty message cannot be retracted after the fact. The only cure is to not create it.

Two adjacent blank-output paths are real. `deliverAssistantMessage` checks truthiness rather than blankness (`host.ts:482`), so a model that ends a turn with a single newline posts a visually blank Slack message; the mrkdwn converter preserves whitespace-only input verbatim (`packages/plugin-slack/src/transport/format.ts:54-117`). And the degraded flush path sends a plain message for whatever `splitForFlush` returns (`stream-bridge.ts:505-509`), where the only rejection is the empty string (`:496`), so a buffer of newlines becomes a whitespace-only post.

### E. "Split-brain on certain models" — under-specified

Nothing in the repository names this symptom. A history search for the phrase returns nothing, and the two matches in the tree are unrelated (`docs/specs/2026-03-18-github-identity-card-design.md:130`, `docs/specs/2026-08-24-platform-hygiene-design.md:126`). The call recorded a one-line report with no reproduction, no model name and no error text. Several independent defects in the transcript-rebuild path produce overlapping symptoms, and picking one of them as "the" cause without evidence would ship a guess. The candidates, with their evidence, are ranked in decision 12.

The common root of the strongest candidates is `entriesToAgentMessages` (`packages/engine/src/thread.ts:3763-3871`), the single function that rebuilds `agent.state.messages` from persisted entries. Three call sites use it: cold rehydrate (`thread.ts:1027-1029`), gate and crash resume (`thread.ts:2007-2012`) and the compaction rebuild (`thread.ts:2614-2619`). It stamps every rebuilt assistant message with `api` and `provider` taken from the session default and a hardcoded `stopReason: "stop"` (`thread.ts:3830-3841`), discarding the persisted value. The persisted value is written correctly, mapping an aborted round to `abort` and a failed one to `error` (`thread.ts:3119-3126`), and it round-trips through the store (`packages/store-postgres/src/helpers.ts:269`, `:333`).

That discarded field changes what the provider sees. The installed transform layer skips errored and aborted assistant messages entirely when it builds a provider request (`node_modules/@mariozechner/pi-ai/dist/providers/transform-messages.js:149-158`), with a comment naming replay of incomplete turns as the reason. A hot thread therefore sends a materially different conversation from the same thread after any rebuild: hot, an aborted round is excluded; rebuilt, it is replayed as if it had completed. That is one thread with two transcripts, which is the closest literal match to the reported words.

## Decisions

### Events tab scope

**1. The subscriptions list scopes to the active workspace owner plus the organization, and the reversal is recorded.** `GET /api/event-subscriptions` gains the standard `?ownerType=&ownerId=` pair and adds an owner predicate when it is present. The predicate is a union: rows owned by the named owner, OR rows owned by the caller's organization. The page sends the pair from `useListOwner()`, so the personal workspace lists your subscriptions and the organization's, and a team workspace lists that team's and the organization's. Organization-owned rows join every workspace because this route creates one for a target of `orchestrator: "org"`, that row belongs to no single workspace, and a row that appeared in no list could never be disabled or deleted from the page that created it. The docstring at `events.ts:42-49` is rewritten to state the new rule, and `events.test.ts:378-391` is rewritten to assert the new behavior with a colleague's row seeded in the same organization. Rationale: the call asked for personal subscriptions only, and the workspace switcher is already the product's answer to "whose things am I looking at", so reusing it costs one predicate and no new concept. Recording the reversal matters more than the code change — a future reader who finds the old docstring and the new query would treat one of them as a bug.

**2. The activity feed keeps organization-wide data and gains a default-on workspace filter.** The route accepts the same owner pair. When it is present the query adds an `EXISTS` over `event_deliveries` joined to `event_subscriptions` on the delivery's subscription, matching the named owner. When it is absent the feed behaves exactly as today. The page renders a two-value control, "This workspace" and "All", defaulting to "This workspace", and sends the owner only for that state. The chosen value lives in the route's `?scope=` search param, not in the feed component, because the Activity and Subscriptions tabs unmount each other. Rationale: hard-scoping the feed would delete its stated purpose. An event that matched nothing you own is precisely the row you open when you ask why your subscription never fired (`feed.tsx:20-25`), and that question is unanswerable from a page that hides those rows. A default-on filter gives the call's requested behavior on first load and keeps the diagnostic one click away. Each `EXISTS` probe is cheap: `event_deliveries_event` indexes the join column (`schema/index.ts:1591`) and the subscription lookup is by primary key. The NUMBER of probes needs a bound of its own, so the filtered query also takes a 30-day lower bound on `received_at` — see deviation 12.

**3. The events page adopts the shipped workspace clause.** `<WorkspaceClause />` renders beside the page title (`events.index.tsx:39`), as it does on the sessions, workflows, memory and skills pages. Rationale: two of the page's surfaces now change meaning with the switcher, and the clause is the one idiom the 2026-08-17 design settled on for saying which workspace a page is showing.

### Workspace switcher scope

**4. The dashboard threads card resolves its assistant from the assistants list, not from the orchestrator info route.** `threads-card.tsx` calls `useListOwner()` and `useAssistants()`, then `defaultAssistantFor(assistants, owner.ownerType, owner.ownerId)` (`packages/web/src/api/assistants.ts:50-59`) to get a `sessionId`, which `AssistantSummary` already carries (`packages/api/src/wire/types.ts:202`). `GET /api/orchestrator/info` is left alone. Rationale: the assistants list already returns the caller's own assistant plus one per team they belong to, so the team case needs no server change and no new endpoint. Widening `/api/orchestrator/info` would instead put a team branch into a route whose remaining job — the persona file and the presence dot — is genuinely personal (`orchestrator.ts:115-121`).

**5. Memory writes carry the owner, and the three client methods gain the parameter.** `writeMemoryDoc`, `deleteMemoryDoc`, `exportMemory`, `importMemory` and `getJournalSummary` take an optional `OwnerFilter` and append it with the existing `ownerQuery` / `ownerSuffix` helpers (`client.ts:218-236`). `MemoryDoc`, the dashboard memory card and the memory import/export panel pass `useListOwner()`, and the invalidation keys in `memory-doc.tsx` gain the same owner so a write invalidates the workspace it wrote to. Rationale: the server already authorizes a named owner on every write route through `resolveScope(c, "write")`, so this is pure wiring. Leaving it unwired is the sharpest defect in this group, because a team-scoped tree currently opens and silently rewrites personal files.

**6. `GET /api/usage/summary` accepts an owner filter, and a team scope narrows both halves.** With no owner, or with the caller's own user owner, the response is byte-identical to today. With `ownerType=team`, the aggregate adds `owner_type = 'team' AND owner_id = $id`: `me` becomes the caller's spend inside that team's workspace, and the comparison block lists that team's spenders. The block gains `scope: "org" | "team"`, and the card's heading follows it. The caller must pass `canViewSession` for the named owner (`packages/api/src/services/session-access.ts:68`), which is the same gate the memory routes use; a caller who fails it gets a 404, matching the existence-hiding convention. Rationale: the view already resolves an owner for every turn, so a team scope is expressible without a schema change. The `scope` discriminator is not optional polish — the card's own comment explains that calling organization rows a team's would misreport whose spend is on screen (`usage-card.tsx:61-64`), and that reasoning applies in the other direction too. Known limit, stated rather than fixed: a team-owned workflow run has no acting user, so `user_id` is null on its rows (`0000_app.sql:957-959`) and it is absent from the per-member breakdown, exactly as it is absent from the organization breakdown today.

### Homepage usage card

**7. The member leaderboard is capped at twenty rows in SQL, and the caller's own row is always present.** The aggregate gains `ORDER BY COALESCE(SUM(cost_total), 0) DESC, SUM(total_tokens) DESC LIMIT 20` behind a `MEMBER_LIMIT` constant beside `DAY_MS` (`usage.ts:29`). If the caller's own id is not among the twenty, the route appends the caller's own 30-day row, which the handler already computed for `me`. The response gains `memberLimit` and `truncated`, and the card labels a truncated list "Top 20 by spend". Rationale for the layer: SQL, not render. Capping at the query bounds the aggregate result, the `inArray` user lookup that follows it (`usage.ts:110-118`) and the serialized payload, whereas capping at render leaves an unbounded array that every future consumer has to cap again. The existing JavaScript sort stays as the stable presentation order over the twenty rows. Always including the caller matters because the card highlights "You", and a leaderboard that silently drops the reader is worse than one that admits it is truncated.

**8. The usage card gets the same height cap as its three siblings, and two pure helpers replace the spread and the flat-bar case.** `usage-card.tsx:36` becomes `className="flex-1 px-4 py-3 space-y-3 overflow-y-auto max-h-64"`, matching `memory-card.tsx:78`. Two exported pure functions join `windowCostDisplay`: `maxMemberCost(members)` folds with `reduce` instead of spreading an array into `Math.max`, and `memberBarWidth(costUsd, max)` returns `null` when `max` is zero or below. `MemberBar` hides the bar track for a null width and shows the name and the em dash alone. Rationale: the card is the only dashboard card without a cap, which makes the missing cap the best-supported reading of "broken"; the cap in decision 7 removes the condition that triggers it, and this change makes the card correct regardless of row count. The two helpers are pure so they are testable without rendering, as `windowCostDisplay` already is. A flat set of two-percent bars beside a column of em dashes is a chart that contradicts its own labels, and hiding the bars is the honest rendering of "no priced spend to compare".

### Slack empty messages

**9. A Slack stream opens on the first flushable non-blank text, not on `message_start`.** `registerStream` stores its opener on the stream as a new `open` field instead of returning it, and the `message_start` branch stops firing it (`stream-bridge.ts:295-300`). The opener runs inside `flushOnce`, once, immediately before the branch that needs a provider message. `flushOnce` reorders so that the empty-buffer check precedes the wait on a pending open, and the wait on a pending open stays where the degraded branch needs it. Rationale: this places the deferral at the one point that already knows there is text to deliver, and it needs no new event and no engine change. The bridge cannot read a stop reason, so a guard at `message_start` is not available to it; a guard at the flush is.

**10. A stream that never receives a delta is closed without ever existing, and an abnormal ending still opens one.** With decision 9, a tool-only round leaves an in-memory `ActiveStream` and nothing else: no Slack message, and no `active_streams` row, because the durable row is inserted only inside `openRef` after `startStream` resolves (`stream-bridge.ts:404-406`). `finish` then flushes an empty buffer, returns at the first guard, and `closeRef` returns early because `stream.ref` is null (`:645`). Nothing is posted and the orphan sweep has nothing to sweep. When `finish` carries a note — the abort, error and api-restart cases (`stream-bridge.ts:227-229`, `:314-318`) — the note is appended to the buffer before the flush, so the opener runs and the reader gets a message saying what happened. Rationale: silence after a "is thinking…" status is worse than a one-line message, and an abnormal ending is exactly the case where the reader needs to be told. There is at most one such message per turn.

**11. Blank assistant text never becomes a new Slack message.** In `flushOnce`, when the split's `send` is blank and no provider message exists yet, a non-forced pass reschedules and a forced pass discards the blank text. Whitespace appended to an already-open message keeps its current behavior, which `appendStream` already tolerates (`transport.ts:547`). On the discrete path, `host.ts:482` becomes `if (entry.content.trim() !== "")`. Rationale: a model that ends a turn with a newline currently posts a visually blank Slack message that cannot be deleted, and the same blank can reach the plain-message fallback through the degraded flush.

### Split-brain

**12. No fix ships until a diagnostic names the cause.** The candidates, ranked by how well they match "two conversations for one thread":

1. **The rebuild discards the persisted stop reason** (`thread.ts:3837` hardcodes `stopReason: "stop"`). The transform layer skips errored and aborted assistant messages when building a provider request (`transform-messages.js:149-158`), so a hot thread and the same thread after a rebuild send different conversations. Strongest match, and provider-independent in mechanism but loudest where a replayed incomplete turn breaks pairing validation.
2. **The rebuild stamps the session default's `api` and `provider`, not the thread's pin.** All three call sites pass `session.options.model` (`thread.ts:1028`, `:2009-2011`, `:2616-2618`) while the thread's own model lives in `modelOverride` (`thread.ts:271`, `:1116-1118`). The transform layer branches on the `provider`/`api`/`model` triple to decide whether a message is same-model (`transform-messages.js:65-67`), which controls tool-call id rewriting and thought-signature handling. Model-family dependent by construction.
3. **Reasoning blocks are read but never written.** `MessagePart` declares a thinking variant (`packages/engine/src/types.ts:314`) and the rebuild maps it back (`thread.ts:3814`), but nothing produces one: the `message_end` handler composes leading text plus tool calls only (`thread.ts:3110-3114`), and `currentAssistantParts` receives only tool-call parts (`thread.ts:3076-3086`). There is also no field for a thinking signature. Affects reasoning-model families only.
4. **A duplicated user turn on the reactive overflow retry.** `compactThread` replaces `agent.state.messages` wholesale from the DAG (`thread.ts:2614-2619`), after which the `slice(0, -1)` at `thread.ts:2468` no longer operates on the array its comment describes. When the failing round reached `message_start`, an assistant entry with `stopReason: "error"` was persisted, the slice drops that entry rather than the failed message, and the re-prompt at `thread.ts:2469` appends a second copy of the same user message. Whether this fires depends on when the provider surfaces the overflow, which is per-provider.
5. **A silent model downgrade mid-thread.** `resolveTurnModel` falls back to the session default with no event when a pin stops resolving (`thread.ts:1104-1111`), and `resolveTurnModelForTurn` does the same on a null resolver result (`:1147-1148`). Already specified for a loud-fail fix in `docs/specs/2026-08-24-thread-model-pinning-and-compaction-design.md` decision 3.

Rationale: candidates 1, 2 and 3 all fire only after a rebuild, candidate 4 only after a reactive compaction, and candidate 5 at any turn. They are independent defects with overlapping symptoms, and the repository rule is to fix the underlying issue rather than ship a guardrail as the fix. Shipping a diagnostic is cheap and it discriminates all five.

**13. The diagnostic is a transcript fingerprint on the existing tracing seam, plus one environment flag.** A new pure module `packages/engine/src/transcript-fingerprint.ts` exports `fingerprintMessages` over `agent.state.messages` and `fingerprintEntries` over persisted `SessionEntry` values. Each returns one compact line per message — role, stop reason, api, provider, model id and block kinds — joined by a separator. Four call sites record it: the cold rehydrate (`thread.ts:1027-1029`), the resume rebuild (`thread.ts:2007-2012`), the compaction rebuild (`thread.ts:2614-2619`) and the hot send immediately before `agent.prompt` (`thread.ts:2449`). Each records a span event on the active turn span carrying the fingerprint and a source label, and each writes the same line to stdout when `VALET_TRANSCRIPT_DEBUG=1`. Rationale: the engine already depends on the OpenTelemetry facade and degrades to a no-op when no host registers an SDK (`packages/engine/src/tracing.ts:1-33`), so this costs nothing in dev and in tests. Recording both fingerprints at a rebuild makes the divergence visible from a single restart, without needing a before-and-after comparison across two runs: the entries carry the real stop reasons and the rebuilt messages all read `stop`, so candidate 1 shows up as a column difference on one line.

**How to read the result.** Reproduce the report on one Anthropic model and one OpenAI Responses model, then compare. A stop-reason column that reads `stop` in the messages fingerprint where the entries fingerprint reads `abort` or `error` implicates candidate 1. A provider or api column that disagrees with the thread's pin implicates candidate 2. A missing thinking block on a reasoning model, together with a provider error naming a function call without its reasoning item, implicates candidate 3. Two consecutive user lines after a reactive compaction implicate candidate 4. A model column that changes between turns with no pin change implicates candidate 5. If the symptom appears on a thread that was never rebuilt and never restarted, candidates 1 to 3 are excluded and 4 and 5 move up.

## Reconciliation with in-flight work

**#396 `feat/valet-design-spec` (open, 95 files).** Valet Design is implemented on that branch: a `design` session kind, `design_*` engine tool definitions, a shadow-root client renderer, share-link tokens and a schema change. It touches `packages/web/src/api/client.ts`, which decision 5 also edits. No shared function: the design branch adds new client methods, and decision 5 adds an optional parameter to five existing memory and usage methods. **Verdict: no overlap beyond a file-level merge conflict in `client.ts`.** Whichever lands second rebases. ## Known limits

1. **The workspace default buys a single-user organization nothing and still
   costs it the unmatched events.** In an organization with one member, the
   caller's subscriptions are the only subscriptions, so "This workspace" and
   "All" differ by exactly one set: the events that matched nothing. That set
   is the one the page exists to explain. The default therefore hides the
   interesting rows and hides nothing the reader wanted hidden, which is pure
   downside on the shape of every dev-loop stack and most small installs. The
   empty state names the "All" control, so the reader is one click from the
   whole feed and is told so, and the request that produced this pass asked
   for a scoped default. Making the default depend on member count would make
   one page behave differently between two deployments for a reason nobody can
   see, so this pass keeps one default and records the cost here. Revisit if a
   single-member deployment reports the feed as useless rather than merely
   narrow.

## Deviations from this design (recorded at implementation)

Group A shipped first, on branch `fix/events-tab-scope`. Its differences from
the plan above are listed here, and the task text was rewritten to the shipped
behavior in the same commit. The remaining groups append to this section as
they land; the note already written for group D sits under Non-goals and moves
here when that branch ships.

1. **`routes/assistants.ts` imports the shared reader instead of keeping its copy.** Task 1 said `routes/assistants.ts` and `routes/memory.ts` "keep their local copies for now". `assistants.ts` does not: it imports `readOwnerFilter` from `_owner-filter.ts` and its own copy is gone, one import line replacing sixteen. Task 1 defines the shared file as a copy of that exact function, error strings included, so leaving the original in place would have shipped the duplication the finding named. `isOwnerType` stays in `assistants.ts` because the create route validates a request body owner with it (`assistants.ts:105`), which is not a query filter. `routes/memory.ts` is untouched, as are the three other readers that differ in what they return. Open question 6 carries the same answer.

2. **The three subscription mutations invalidate the bare key prefix, not the owner-scoped key.** Task 4 said to add the owner to them. They call `qkEvents.subscriptions()` with no owner instead. The owner is a trailing key element precisely so that the bare prefix matches every cached workspace; scoping the invalidation inverted that rule and left one reader stale — `redeliver-button.tsx` reads the unscoped key on purpose, because redelivery fans out to every matching subscription in the org, and an owner-scoped invalidation never matched it, so a create or a delete left its confirm step counting rows that no longer matched. The `owner` props that existed only to feed the scoped hooks were removed from `SubscriptionRow` and `SubscriptionCreateDialog` with them.

3. **The feed's scope control reads "This workspace" and "All", not "Mine" and "All".** Decision 2, task 5, exit criterion A and open question 1 all said "Mine" when this document was written. The control ships with the labels "This workspace" and "All", `FeedScope` values `"workspace"` and `"all"`, and a `triggerLabel` of `Scope: …`. "Mine" is wrong in a team workspace, where the control sends `ownerType: team`, and this repository names the scope after the workspace and uses one name for one thing. The trigger names the dimension it filters because it sits beside "All services" and "All events". The four sentences above and the amended note in `docs/specs/2026-08-17-team-workspace-ui-design.md` were rewritten to the shipped labels rather than the code to the written ones.

4. **Both workspace-scoped queries are held until the owner resolves.** No task asked for this. `EventFeed` passes `{ enabled: scope === "all" || owner !== undefined }` to `useEvents` and `SubscriptionsPanel` passes `{ enabled: owner !== undefined }` to `useEventSubscriptions`; both loading rows read `isPending` rather than `isLoading` so a held query still shows as loading. `useListOwner()` answers `undefined` while the caller's identity is in flight, and an owner-less request IS the organization-wide list on both routes, so without the gate a page whose header names the active workspace renders the whole organization for one frame and then drops it. `packages/web/src/lib/use-list-owner.ts` names this gate as the remedy for a surface that must not show another workspace's rows even briefly. The panel needs it more than the feed does, because its rows carry a mutation control: an unheld first frame offers switches over colleagues' automations. Tasks 4 and 5 now state it, and `-subscriptions-panel.test.tsx` pins the held and the resolved state of each surface.

5. **The `EXISTS` subquery repeats the organization predicate.** Task 3 named the join and the owner pair only. The subquery also filters `eq(eventSubscriptions.orgId, user.orgId)`, so the join cannot reach a subscription row from another organization even if a delivery ever crossed one. The outer query is already organization-scoped; this is defense in depth on a cross-table join, and it costs nothing on an indexed lookup.

6. **The route suites carry three cases beyond the ones the tasks name.** Task 2 asked for three subscription cases and task 3 for one feed case. Shipped as well: a fourth subscription case for a team owner, a feed case that combines the owner filter with the key filter, and a feed case for a half-specified pair. The half-pair message is asserted through one `HALF_FILTER_ERROR` constant in `events.test.ts`, because one web client builds the owner query for every list that takes it, and the workflows and skills suites assert the same string.

7. **`packages/api/src/routes/github-app.test.ts` is edited by this branch, and no task names it.** The webhook ingest case asserted `deliveryRows[0].status === "pending"`. Ingest nudges the in-process dispatcher fire-and-forget — `events/ingest.ts` calls `deps.onIngest?.()` outside the transaction — so the row holds `"pending"` only until the dispatcher wins the race, and the case failed whenever delivery landed first. The assertion now accepts `"pending"` or `"delivered"` and keeps what the case exists to pin: ingest matched the subscription and wrote exactly one delivery for it. The terminal status is `events/dispatcher.test.ts`'s to assert. The fix is unrelated to the events scope change and was made on this branch because the race turned the case red here.

8. **The scoped subscriptions list is a union with the organization's own rows.** Decision 1 and task 2 both said one owner, one predicate pair. Shipped as `owner OR ownerType = 'org'`. `POST /api/event-subscriptions` writes three owner types, and the create dialog's "Notify the org assistant" option produces the third. `useListOwner()` emits only `user` or `team`, so a strict pin on both owner columns dropped every organization-owned row out of every workspace: the page created subscriptions that appeared in no list, could never be disabled or deleted from the UI, and kept firing on every matching webhook. The fix is on the server, because an organization-owned subscription is organization-wide by construction and belongs in every workspace's list; a colleague's personal row still does not. `useCatalogOwner` was rejected for this: it sends no pin at all in the personal workspace, which would re-list every colleague's row and undo the change. The panel comment claiming the list carries every subscription in the organization was rewritten, and `owner-badge.tsx`'s claim that no route creates an organization owner was corrected — the badge still renders nothing for one, because it links to the owning TEAM's assistant, and the subscriptions panel labels its own organization rows.

9. **The feed scope is a route search param, not component state.** Task 5 put the control in `feed.tsx` and said nothing about where its value lives, so it shipped as `useState` inside `EventFeed`. The Activity and Subscriptions tabs unmount each other, which discards the choice on exactly the round trip a diagnosis needs: select "All" to find an event that matched nothing, open the Subscriptions tab to read the rule, come back, and the event is hidden again. `?scope=` now holds it. `EventFeed` takes `scope` and `onScopeChange` as props and the route owns the value, which also makes an org-wide feed a link someone can paste. Only `"all"` is written; an absent or unrecognized value reads as the workspace default.

10. **The Refresh control is disabled for the length of the hold.** Deviation 4 held the query with `enabled`, which is not the whole gate: `refetch()` ignores `enabled` in react-query v5, so a press during the hold fetched the organization-wide feed and rendered it under a control reading "This workspace". The feed hoists the gate into one `canFetch` value, passes it as `enabled`, and disables the Refresh button while it is false.

11. **Known limit: ownership follows the target, so a team-created workflow subscription is filed personally.** `POST /api/event-subscriptions` derives the owner from the target and nothing else: an orchestrator target names its own owner, and every other target is filed to the caller. A subscription created in a team workspace against a team workflow is therefore written `user`-owned, and it disappears from the Subscriptions tab it was created in, under an empty state saying none exist. It is not orphaned — the workflow's own Triggers surface still lists it — so this is misfiling, not loss. The branch does not change the derivation, because deciding whether a workflow target should inherit the workflow's owner or the active workspace's is a change to how every subscription is owned, and the two answers disagree for a personal subscription on a team workflow. The create dialog states the outcome instead: while a team workspace is active and the selected target would file the row personally, it reads "Ownership follows the target. This subscription will be listed in your personal workspace, not in <team>." Organization targets need no note, because deviation 8 lists organization-owned rows in every workspace.

12. **The owner-filtered feed carries a 30-day window; the unfiltered feed does not.** Decision 2 called the `EXISTS` cheap and stopped there. Each probe is cheap; the count of probes is not. `LIMIT 50` bounds the unfiltered feed because `events_org_received` covers `(org_id, received_at)` and the scan stops after fifty index entries. With the filter on, the `EXISTS` rejects rows the index cannot pre-select, so a workspace whose subscriptions have matched nothing walks the organization's whole event history to fill a page it can never fill. Measured on PGlite with 40,000 organization events and no matching delivery: 40,000 semi-join loops, 200,689 buffer hits, 104 ms for one empty page, growing linearly with history. The same query with a `received_at` lower bound: 1,001 loops, 5,026 hits, 2.4 ms. The bound joins the existing index condition, which is why it is the cheapest bound available and why no new index is added.

    What it costs: a workspace whose newest matching event is older than 30 days sees an empty scoped feed although older matches exist. The page states the window rather than hiding it — the scoped empty state reads "in the last 30 days", and a scoped list with rows carries a line naming the window and pointing at "All". "All" has no window, so the full history stays one click away, which is the same reason decision 2 refused to hard-scope the feed. `OWNER_FEED_WINDOW_MS` in the route and `WORKSPACE_WINDOW_DAYS` in `feed.tsx` are the two places to change together.

13. **Both held queries have a terminal state, because the hold can be permanent.** Deviation 4 held each workspace-scoped query on `owner !== undefined`. `useListOwner()` answers undefined while identity loads AND when identity fails, so a permanent `useMe` failure held the query for the length of the session: the Activity tab read "Loading events…" and the Subscriptions tab "Loading subscriptions…", with no error and no way out. Both surfaces now read the identity query directly and report the failure. The feed's message names the "All" control, which asks for no owner and is therefore still reachable. The Subscriptions tab has no such control — an unscoped list is not a state that tab offers — so its message names the only move the reader has left, which is to load the page again.

14. **A held workspace query gets a cache key of its own.** Deviation 4 held each scoped query with `enabled`, which stops the request and nothing else: react-query still computes the key, and `qkEvents.feed(service, key, undefined)` is the key the "All" state uses. A held feed therefore shared one cache entry with the unscoped feed, so a warm "All" answer rendered under a control reading "This workspace". The subscriptions list had the same collision against `redeliver-button.tsx`, which reads the unscoped list on purpose (deviation 2). `ownerKey` now takes a third state and appends `"owner-unresolved"` for a scoped query whose owner has not resolved yet. The marker is trailing like an owner pair, so the bare prefix that the three mutations invalidate still reaches it.

15. **The scoped feed carries the same org branch the scoped subscriptions list carries.** Deviation 8 unioned org-owned rows into the subscriptions list and left task 3's feed predicate as the plain owner pair. The two surfaces are the two tabs of one page, so the asymmetry was visible: an org-owned subscription was listed in every workspace while every event it received was missing from that workspace's feed, and the feed's empty state contradicted the tab beside it. The `EXISTS` now matches `owner OR ownerType = 'org'`, the router docstring no longer claims the feed narrows to the workspace alone, and the amended note in `docs/specs/2026-08-17-team-workspace-ui-design.md` states the union for both. The window and the org predicate inside the subquery are unchanged.

## Non-goals

The events table gains no owner column, and the feed's meaning does not change on the server: the default response is still every event in the organization. Nothing here builds a per-row ownership badge on the events page; the badge idioms are inconsistent across the product and unifying them is its own change. The usage route computes no organization-wide total, and team-owned workflow spend stays absent from the per-member breakdown for the same reason it is absent today. No spend cap, warning or enforcement is in scope — that is the spend-limits design. Group D adds no Slack message deletion, because the transport has no delete capability, and it does not add a Slack transport spec, which #162 owns. Group E ships no fix for any split-brain candidate; the fixes for candidates 2 and 5 belong to the thread-model-pinning and compaction design, and the fix for candidate 1 waits on the pi-ai version question.

**Deviation recorded for group D.** The Slack streaming transport has no dated design spec in `docs/specs/`, so the deferred-open rule is recorded here instead of in a subsystem spec: a Slack stream is opened on the first flushable non-blank text, never on `message_start`, and a round that produces no text produces no Slack message. The follow-up that lands #162's documents must carry this rule into them.

## Open questions

1. **Should the activity feed default to the active workspace or to "All"?** The call said personal subscriptions only, which is unambiguous for the subscriptions tab and silent about the feed. **Recommended default: "This workspace".** It matches the call's direction on first load, and the diagnostic view is one click away rather than gone.

2. **Should `OwnerBadge` become a four-way badge so organization-owned rows are labelled?** It returns null for everything except a team (`packages/web/src/components/owner-badge.tsx:32`), so an organization-owned skill on a detail page renders identically to a personal one, while the skills grid labels it correctly through a second component. **Recommended default: not in this bundle.** It touches six call sites and three competing idioms, which is a change of its own size.

3. **Should `SlackTransport.send` reject blank input directly?** Its return type is a `SendRef` with a required message id, so an early return would have to invent one. Decision 11 guards every caller instead. **Recommended default: no.** Revisit if a third caller appears.

4. **Should `markStreamed` also defer to the first delta?** Deferring it would let the host deliver a turn-final message whose text never arrived as deltas. That shape cannot occur today, because the engine emits a delta for every text chunk (`packages/engine/src/thread.ts:3057-3062`), and deferring would break the marker's documented synchronous contract and the test that pins it (`stream-bridge.test.ts:619-633`). **Recommended default: no.** Revisit if a non-streaming provider is ever added.

5. **Which split-brain candidate gets fixed first if the diagnostic implicates two at once?** **Recommended default: candidate 1**, the discarded stop reason. It is one line, it is provider-independent in mechanism, and it is the only candidate that makes one thread send two different conversations with no configuration change involved.

6. **Should the duplicated owner-filter readers be collapsed?** **Answered at implementation: only the identical one.** `routes/assistants.ts` held the exact function task 1 extracts, so it imports the shared reader instead of keeping a byte-identical copy. The other four readers stay: `routes/memory.ts` throws, `routes/skills.ts` returns a status with the error, `routes/workflows.ts` returns a workflow owner ref rather than a principal, and `routes/sessions.ts` reads the pair inline and admits only `user` and `team`. Converting those changes error handling in ten route bodies, which does not belong in a bundle of small fixes.
