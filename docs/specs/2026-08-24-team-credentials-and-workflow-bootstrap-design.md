# Team Credentials and Workflow Bootstrap Design

**Date:** 2026-08-24
**Status:** Implemented 2026-09-06 (PRs #572 to #591)
**Scope:** Two halves of one 2026-08-24 request. Half 1 makes team-owned execution possible: the `CredentialOwner` union gains `team`, team credential rows exist in two forms (direct and delegated-by-reference), and both the workflow action invoker and live sessions resolve them. Half 2 gives a new team its default workflows. The 2026-08-24 planning call changed the direction of Half 2: default workflows now come from a GitHub repository through template sync, not from a list declared in `valet.yaml`. This spec therefore owns only the team side of that arrangement — which repository a team draws from, who may configure it, what happens when a team is created, and what happens when a team is deleted. The sync mechanism itself belongs to `docs/specs/2026-08-24-workflows-mvp-design.md`, and this spec depends on three named functions from it rather than restating its design. RBAC permission vocabulary stays out of scope; the direct `isTeamMember` and `canAdministerTeam` checks remain the gates, for the reason given under "Reconciliation with in-flight work".

All file and line citations in this document are historical: they were read on `tkhq/dev-v2` at commit `e33701dc`, before the implementation landed, and the lines they name have moved since.

## Context

Teams can own workflows, sessions, and assistants today, and every read path enforces live membership: `isAuthorizedForOwner` for workflow definitions (`packages/api/src/workflows/service.ts:160-168`), and `canViewSession` / `canAdministerSession` for sessions (`packages/api/src/services/session-access.ts:68-75` and `:95-102`). Execution is where team ownership breaks.

`CredentialOwner` allows only `user`, `org`, and `session` (`packages/engine/src/types.ts:563-566`). The workflow action invoker maps a run's owner `Principal` through `credentialOwnerFor`, which returns null for a team principal (`packages/api/src/plugins/action-invoker.ts:550-555`), and the invoker then refuses with the message "credential resolution is not supported for owner type team" (`action-invoker.ts:209-215`).

Three of the four trigger paths start a run as the workflow definition's owner: the scheduler (`packages/api/src/workflows/scheduler.ts:164-167`), the event dispatcher (`packages/api/src/events/dispatcher.ts:246-249`), and the webhook route (`packages/api/src/routes/workflow-hooks.ts:78-81`). The manual path hardcodes the invoking user instead (`packages/api/src/workflows/service.ts:752-755`). A team-owned workflow with tool nodes therefore works when a member clicks Run, and fails on every tool node when its schedule fires. The coupling is accidental, and it hides the defect from anyone who tests by hand.

Live sessions carry an owner principal (`SessionOptions.owner`, `packages/engine/src/types.ts:1831`; the host passes it at `packages/api/src/engine/host.ts:1454`), and the session stores it as `this.principal` (`packages/engine/src/session.ts:273`). `Session.credentialProvider()` ignores it and builds `{ type: "user", id: this.options.userId }` unconditionally (`session.ts:1342-1343`). A team assistant session's `userId` is the synthetic actor id `team:{teamId}` (`packages/api/src/workflows/engine-deps.ts:198-200`), so its credential reads can never hit a real row.

A second reader sits behind that one. When the host supplies a `credentialResolver`, it replaces the raw store read for every service (`session.ts:1345-1349`). That resolver is `EngineHost.buildCredentialResolver` (`packages/api/src/engine/host.ts:999-1080`), and its Slack branch states the assumption in a comment: "The engine's session always calls the resolver with a user owner" (`host.ts:1043-1046`). Its GitHub branch calls `resolveSessionGitHubToken` with the closure's `userId` (`host.ts:1059-1070`), which for a team session is the synthetic `team:{teamId}` string. Making sessions owner-aware without touching this resolver would send a synthetic id into GitHub token resolution.

The credential store is already owner-generic. `owner_type` is plain text and the primary key is `(owner_type, owner_id, service)` (`packages/api/src/schema/index.ts:1087-1106`). Adding a team owner needs no migration. The OAuth refresh decorator wraps the store at `packages/api/src/providers/node.ts:336`.

Org-level identities exist in two shapes. A service that declares `requires.orgCredential` (`packages/engine/src/valet-plugin.ts:81-87`; only `packages/plugin-slack/src/plugin.ts:51` declares it) is provided by one org-scoped credential, and the invoker already escalates to it for that service alone (`action-invoker.ts:265-271`). The GitHub App is the second shape: a tool node with `credential: "app"` mints an installation token for the repository named in its own parameters. Slack identity enrichment applies to user owners only, by design (`action-invoker.ts:274-285`).

On the bootstrap side, there is no hook at all. `createTeam` inserts exactly two rows — the team and the creator's admin membership (`packages/api/src/services/teams.ts:253-285`). Template install is a manual, per-user act (`installWorkflowTemplate`, `packages/api/src/workflows/templates.ts:726`, transactional body `:965-1069`), and it refuses a team install when the template has both a schedule and tool nodes, precisely because a scheduled team run cannot resolve credentials (`templates.ts:802-815`, code `unsupported_owner`).

The repository-sync rail the call refers to already exists, and it already understands team ownership. `skill_sources` carries `(org_id, owner_type, owner_id)` with `owner_type` in `user | team | org`, a `created_by` column, a repository address, and full poll and backoff state (`packages/api/src/schema/index.ts:901-945`). `packages/api/src/services/skill-source-credential.ts:1-70` holds the whole tenancy rule in one function: a user source syncs with that user's GitHub credential, a team source with the credential of the user named in `created_by`, an org source with the org's GitHub App installation token, and every failure falls to an anonymous read rather than climbing to a stronger token. The bindings are re-checked on every sync, not at creation. Creating a team source takes the team ownership lock and re-checks membership before it writes (`packages/api/src/services/skill-sources.ts:216-224`); creating an org source requires an org admin at the route (`packages/api/src/routes/skills.ts:617-627`). Deleting a source deletes its mirrored rows in one transaction (`skill-sources.ts:368-372`).

Two facts about that rail bound what Half 2 can assume. The dot-directory rule opens exactly one dotted directory, `.claude`, so `.valet` is excluded today (`packages/api/src/services/skill-discovery.ts:126-128`). And `workflow_definitions` has no `origin`, `source_id`, or repository column (`packages/api/src/schema/index.ts:963-976`), so no workflow row can be attributed to a repository yet. Both gaps belong to the workflows MVP spec.

Deletion is the last piece. `deleteTeam` deletes the team's skills and its tracked repositories (`packages/api/src/services/teams.ts:564-569`) but refuses while the team owns any workflow (`assertNoTeamOwnedWorkflows`, `teams.ts:498-505`, called at `:563`). Once a team receives workflows at birth, every team becomes undeletable until someone removes its workflows by hand.

Attention fan-out already handles teams. `resolveAudience` routes a team-owned run's notifications to all members, and an escalation to team admins only (`packages/api/src/orchestrator/attention.ts:98-110`). No new fan-out is needed.

## Decisions

### Half 1 — team credential execution

**1. `CredentialOwner` gains `"team"`.** The union at `packages/engine/src/types.ts:563-566` grows one member. The store already accepts arbitrary owner strings and its primary key already spans `(owner_type, owner_id, service)`, so this is a type-level and resolution-layer change with no migration. Adopted unchanged from the 2026-07-21 team-resources design.

**2. Two kinds of team credential share one keyspace.** A *direct* team credential is a token a team admin stores under `{ type: "team", id }`. A *delegated reference* is a row a member creates that holds no secret material — only `metadata: { delegatedFrom: userId }` plus the source credential's `type`. The primary key keeps the one-credential-per-service-per-team invariant visible: delegating into an occupied slot returns 409.

**3. Delegation is by reference, never by copy, and there is no actor fallback.** Resolution follows the reference to the delegator's live user credential at use time, after it re-checks that the delegator is still a member of the team. A missing source credential or a lapsed membership throws a typed `CredentialReferenceBrokenError` whose message names the corrective action: reconnect the service, re-delegate it, or store a direct team credential. A team-owned run never falls back to the triggering member's personal credentials. A team workflow that works for one member and fails for another is a debugging trap, so failing uniformly is the feature.

**4. Reference resolution wraps outside the refresh decorator.** A `TeamCredentialStore` decorator composes around `OAuthRefreshingCredentialStore` (`packages/api/src/providers/node.ts:336`). A followed reference then refreshes through the source user's row, and a direct team credential refreshes under the team owner. Deleting a user credential cascades: every team reference row whose `metadata.delegatedFrom` names that user for that service is deleted in the same request, because a reference must never outlive its source.

**5. A team-owned read stops at the team, except for services that declare an org credential.** `credentialOwnerFor` returns `{ type: "team", id }` for team principals, and the refusal at `action-invoker.ts:209-215` is retired. The existing `requires.orgCredential` escalation (`action-invoker.ts:265-271`) then applies to team owners exactly as it applies to users, so a team run's Slack node resolves the org bot token when the team holds no Slack credential. No other service escalates. A general team-to-org fallback would let an org-wide credential silently back a team run, which is the same debugging trap decision 3 closes.

**6. Sessions resolve credentials from their owner principal, and the host resolver learns non-user owners.** `Session.credentialProvider()` derives the `CredentialOwner` from `this.principal` (`session.ts:273`) instead of hardcoding a user owner. User sessions are byte-identical to today, because their principal already defaults to `{ type: "user", id: userId }`. Because the host resolver replaces the store read for every service when it is present (`session.ts:1345-1349`), `buildCredentialResolver` (`host.ts:999-1080`) gains an owner-aware branch at its head:

- For a non-user owner, the `github` branch calls `resolveSessionGitHubToken` with `auth: "app"` and no `userId` (`packages/api/src/services/session-github-token.ts:71-80` accepts both), so a team session mints an installation token and never resolves a synthetic `team:{teamId}` id as a person.
- For a non-user owner, the `slack` branch reads the team row and then the org bot token, and skips identity enrichment, which matches decision 8.
- Every other service reads the store at the team owner, which routes through the decorator from decision 4.

**7. Manual runs use the definition owner, like the other three trigger paths.** `startWorkflowRun` passes `{ ownerType: row.ownerType, ownerId: row.ownerId }` (`packages/api/src/workflows/service.ts:752-755`). For a user-owned workflow this changes nothing, because authorization already guarantees that the owner equals the invoker. To keep "who ran it" after the fix, `workflow_runs` gains a nullable `actor_user_id` column, recorded on manual runs and left null on unattended triggers. The column is for display and audit only. Run-time context keeps deriving from the owner principal (`packages/api/src/workflows/engine-deps.ts:186`).

**8. A team-owned Slack run uses the org bot token, and private reads fail closed.** Identity enrichment stays user-only (`action-invoker.ts:274-285`). A team has no single person whose channel membership could authorize a private-channel read, so the resolved bot credential stays bare and `plugin-slack`'s own guards refuse. This is locked as intended behavior. Posting to a public channel, which is what most seeded workflows need, works on the bare bot token.

**9. Credential routes gain a team scope and a delegation pair, gated by the existing team checks.** `GET`, `PUT`, and `DELETE /api/credentials/:service` accept `scope=team&teamId=…`. GET requires `isTeamMember` (`packages/api/src/services/teams.ts:411`); PUT and DELETE require `canAdministerTeam` (`teams.ts:443-455`), which already grants an org admin the recovery override. `POST /api/credentials/:service/delegate` with body `{ teamId }` lets any member share a service they have connected with a team they belong to. `DELETE /api/credentials/:service/delegations/:teamId` lets the delegator revoke without any team permission, because the credential is theirs. Team-scope GET summaries mark delegated rows with the delegator. The team-scoped OAuth *connect* flow is deferred: delegation already covers OAuth services, because refresh follows the source user's row, and manual token entry covers API-key services.

### Half 2 — repository-backed team workflows

**10. A team's default workflows come from a GitHub repository, not from a configuration key.** The earlier draft of this spec declared the default set in `valet.yaml` under `org.teamTemplates`. That key is dropped and no replacement key is added. The 2026-08-24 call put templates in a repository so that both open templates and org templates are defined there, and a repository gives the set the three properties a configuration list cannot: review before a change takes effect, history after it does, and one address that the workflow sync and the template sync share. A deployment that edits `valet.yaml` today loses nothing, because the key was never implemented.

**11. A team draws from repo-source rows, and this spec adds no sync code.** The rail is the one that already exists: `skill_sources` plus the sweep in `packages/api/src/services/skill-sync.ts`. A team's workflows arrive from at most two places. Its own team-owned source is a repository a team admin registers for that team alone, and it syncs under the existing team rule, with the credential of the user in `created_by`, re-checked at read time. The org's template repository is an org-owned source, registered by an org admin, syncing with the App installation token, and each team receives its own row pointing at it (decision 13). Nothing in this spec reads GitHub, walks a tree, or writes a workflow row. The three things it needs from `docs/specs/2026-08-24-workflows-mvp-design.md` are named in decision 18.

**12. Registering or removing a team-owned repository requires team administration; reading one does not.** `createSkillSource`'s team branch checks `isTeamMember` today (`packages/api/src/services/skill-sources.ts:216-224`), and `deleteSkillSource` inherits the same member-level rule through `isAuthorizedFor` (`packages/api/src/services/skills.ts:128-140`). Once a source can install runnable and schedulable workflows into a shared team, member-level authority is too low for those two writes: one member could arm work that bills the whole team and posts as the team. Both gain an explicit `canAdministerTeam` check for a team-owned row, which also grants the org admin the recovery override that function already carries (`packages/api/src/services/teams.ts:443-455`). `isAuthorizedFor` itself is left alone, so listing sources and reading one stay member-level — the same read-write split every other team surface uses. A team source that carries only skills tightens with it, which is the right side to err on for the same reason: a team source already spends the creator's GitHub credential on the team's behalf. Personal and org sources keep the gates they have.

**13. A new team adopts the org's template repositories, and the sync runs after the transaction commits.** Inside `createTeam`'s existing transaction, after the two inserts, one team-owned `skill_sources` row is written for each enabled org-owned workflow source in the org, copying `repo_full_name`, `ref`, and `subpath` and setting `created_by` to the creator. The transaction stays free of network calls, so team creation is still one short database round trip and the team ownership lock is never held across a GitHub read. The route then calls `skillSync.syncOnce` for each new row after the transaction commits, so the team's workflows appear immediately rather than at the next fifteen-minute sweep. A failed first sync is reported on the row, which is how source creation already behaves (`packages/api/src/routes/skills.ts:644-647`). A team created when the org has no workflow source adopts nothing, and creation is byte-identical to today.

Per-team rows are used rather than one org row fanned out across teams because the sweep's first change check stops on an unchanged head commit (`skill-sync.ts:22-40`). A fan-out design would skip a team created while the repository sat still, and would give that team nothing until someone pushed a commit. A per-team row has its own poll state, so its first sync always performs the full read.

**14. An adopted row reads the org's template repository with the App installation token.** `resolveSkillSourceCredential` (`packages/api/src/services/skill-source-credential.ts`) gains one branch ahead of its team branch: a team source syncs with the org's App installation token when an enabled org-owned source in the same org names the same `repo_full_name`, `ref`, and `subpath`. Otherwise the team branch applies unchanged.

This is a deliberate, bounded exception to that module's "fails to anonymous, never up" rule, and the boundary is what makes it safe. It is not the `auth: "auto"` ladder, which would let any team source reach every repository the App can see. It grants exactly one repository, and only a repository an org admin has already published org-wide by creating the org source, which is itself an org-admin-only act (`routes/skills.ts:617-627`). Like every other binding in that module it is re-checked on each sync, so deleting or disabling the org source drops the team row back to the `created_by` credential and then to anonymous. The lookup reads the org's own sources through the `skill_sources_owner` index prefix `(org_id, owner_type)` and matches the address in memory; an org holds few org-owned sources, so this costs one small indexed read per sync. Skills mirrored from that same repository into the adopting teams get the same token, which is the intended consequence: an org admin published the repository to the org.

**15. Whether a team workflow arms its triggers is decided by one exported readiness predicate.** A new module `packages/api/src/workflows/team-service-readiness.ts` exports `teamServiceReadiness(deps, { orgId, teamId, definition })`, returning the services a team-owned definition can act as and the ones it cannot, each blocked service carrying the reason. A service is ready when any of three conditions holds: the team has a credential row for it, direct or delegated; the service is in `orgProvidedServiceSet` (`packages/api/src/services/integration-availability.ts:144`); or every tool node naming that service pins `credential: "app"` and `loadAppConfig` (`packages/api/src/services/github-app.ts:208`) reports a configured App.

This replaces the per-user requirement gate in `installWorkflowTemplate` (`templates.ts:773-796`) for team-scoped work. The creator's personal connections are irrelevant to a workflow the team owns. Two callers use the predicate. A gallery install into a team skips a template whose services are not all ready, names the missing service, and installs nothing broken. The workflows MVP spec's reconcile must not arm a schedule, a webhook, or an event subscription for a repo-synced team workflow whose services are not ready; the definition still lands, so a member can see it and an admin can connect the missing service. A workflow that fires nightly and fails nightly is worse than one that waits.

**16. `deleteTeam` reaps team-owned workflows instead of refusing.** The guard becomes a check for active runs rather than for any workflow. Deletion proceeds when no team-owned workflow has an unsettled run, and it cascades definitions, versions, schedules, event subscriptions, and webhooks — the same cleanup `deleteWorkflowDefinition` performs (`packages/api/src/workflows/service.ts:695-719`). This follows the precedent the same function already sets for skills (`teams.ts:564-566`): a workflow definition is a document and a run is the running thing, so only runs block. Settled run rows stay as history, unreachable from list views once the team is gone. To avoid the documented `services/teams.ts` to `workflows/service.ts` import cycle (`teams.ts:496-497`), the reap is injected: `deleteTeam` accepts a `reapOwnedWorkflows(tx)` callback that the route composes from a workflows-side helper. The team's tracked repositories are already deleted here (`teams.ts:567-569`), so repo-origin rows also disappear through the source cascade; the reap covers locally authored team workflows as well and is the belt-and-suspenders for both.

**17. The install refusal for scheduled team templates is removed.** The `unsupported_owner` branch (`templates.ts:802-815`) goes in the same change that lands decision 5. Its stated reason — that a scheduled team run has no connected account to act as — stops being true. Schedules armed at install already run as the team, because the scheduler bills the definition's owner (`scheduler.ts:158-167`), and decision 7 makes a manual test run of the same workflow behave identically. Decision 15's predicate replaces it with a check that names the actual missing service.

**18. Boundary with the workflows MVP spec.** That spec owns the sync mechanism end to end: opening `.valet` in the dot-directory rule (`skill-discovery.ts:126-128`), the discovery rules for the `.valet` and `workflows` folders, the `origin` and `source_id` columns on `workflow_definitions`, the reconcile that mirrors and deletes rows, and the distinction between an open template and an org template. This spec consumes exactly three things from it, and nothing else:

- `listWorkflowSources(db, { orgId, ownerType, ownerId })` — the repo-source rows that carry workflow content, so decision 13 knows which org sources to adopt.
- A `syncOnce` that mirrors a source's workflow content into `workflow_definitions` under the source's owner tuple, scoped by `source_id` and `origin='repo'`.
- A source-delete cascade that removes mirrored workflow rows and their triggers in one transaction, the way `deleteSkillSource` already does for skills (`skill-sources.ts:368-372`).

If that spec spells any of the three differently, this spec adapts at one call site each. Half 1 has no dependency on it and ships on its own.

## Reconciliation with in-flight work

**PR #151 `feat/rbac-permissions` (open, last touched 2026-07-30, 57 files, +2649/-312) — supersede its spec-only half; do not block on the branch.**

The branch carries `docs/specs/2026-07-21-team-resources-design.md`, which is the design this spec adopts. It implements none of it. A file-by-file read of `gh pr diff 151 --name-only` shows no `packages/engine` diff, no change to `packages/api/src/plugins/credential-store.ts` or `action-invoker.ts`, no team credential rows, no delegation routes, and no team permission vocabulary. Its only credential change is three lines in `packages/api/src/routes/credentials.ts` that swap `user.role !== "admin"` for `can(user, "credentials:org")` on the org scope. Its `permissions.ts` declares five org-level permissions and a `can(principal, permission)` with no resource argument; the `TEAM_PERMISSIONS` list and the `can(…, { teamId })` overload that the team-resources design names as Phase A's starting point do not exist on the branch. Its schema change is the `admin | operator | member` role enum on `invites` and `org_members`, nothing more.

Cherry-picking the credential half out of #151 is therefore not an available option, because there is no credential half to pick. The choice is between blocking on #151 and taking the design without the branch. This spec takes the design. `docs/specs/2026-07-21-team-resources-design.md` is added to `docs/specs/` in this pass, which is what `docs/specs/2026-08-17-team-workspace-ui-design.md:96-98` already asks for ("the spec file is not in this tree — land it with the implementation"), and this spec supersedes its Phase A. Decisions 2 through 6 and 9 are that phase, restated with current citations and with the host-resolver work the 2026-07-21 text did not anticipate. Phases B and C of that design have already shipped on `dev-v2` without Phase A.

The position on the branch itself is that it should be revived and rebased on its own track, after this pass, with three changes. It should drop `docs/specs/2026-07-21-team-resources-design.md` from its diff, because this spec now carries and supersedes it and two copies of one design in the tree is worse than none. It should be rebased before review rather than merged as it stands, because it reports `mergeable: UNKNOWN` after twenty-five days and because PR #392 also edits `auth/invites.ts` and `auth/provisioning.ts`. And it should keep the live Keycloak pass its own description calls out as owed before merge.

The claim that RBAC vocabulary stays out of scope is still coherent, and it is now forced rather than merely convenient. `packages/api/src/auth/permissions.ts` does not exist on `dev-v2` at all. Writing this spec's routes against `can(…, { teamId })` would make it undeliverable until a stale fifty-seven-file branch merges, for no gain: the gates it needs, `isTeamMember` and `canAdministerTeam`, are already the gates every other team surface uses (`packages/api/src/routes/teams.ts:314`, `session-access.ts:95-102`) and neither function appears in #151's file list, so the two passes cannot conflict. When #151 does land, the forward path is mechanical. Both checks are single-call predicates evaluated at the route boundary, so a follow-up maps `isTeamMember` onto `team:resources:use` and `canAdministerTeam` onto `team:credentials:manage` with no change to route shape or to any test's assertions about status codes.

**PR #163 `feat/onepassword-credentials` (open, last touched 2026-07-22, 38 files, +4478/-66) — extend it if it lands first; otherwise it extends this.**

It edits four files this spec also edits: `packages/api/src/providers/node.ts`, `packages/api/src/engine/host.ts`, `packages/api/src/plugins/action-invoker.ts`, and `packages/api/src/routes/credentials.ts`. Its central move is architectural. It introduces `packages/api/src/services/credential-resolution.ts` with `resolveUserCredentialRead` and `resolveOrgCredentialRead` as the single read implementation for all three credential readers, which is a different composition point from this spec's decision 4 decorator. The two are compatible in either order, and the merge rule is stated here so whoever goes second does not have to invent it. If #163 lands first, decision 4's rule moves into that module as a third function, `resolveTeamCredentialRead`, keeping the same semantics: follow the reference, re-check membership, throw the typed broken-reference error, never fall back to the actor. If this spec lands first, #163 adds 1Password reference resolution inside the decorator chain rather than beside it. Neither ordering changes any decision above.

One behavior in #163 needs an explicit position, because it points the other way from decision 5. Its module header records a deliberate change: a user-owner miss falls back to the org row for every credential kind, not only for 1Password references. This spec does not extend that to team owners. A team-owned read stops at the team unless the service declares `requires.orgCredential`. The reason is decision 3's: a team run that silently borrows an org-wide credential is indistinguishable from one that resolved its own, and the first failure then looks like a missing credential with no history. Whichever pass lands second should align the two rules deliberately rather than by accident; the open questions record the recommended default.

Both edit `packages/api/migrations/pg/0000_app.sql`, and #396 also adds an `agent_sessions.kind` value. Neither touches credentials, team ownership, workflow ownership, or the repo-source rail. **PR #392 `security/single-line-fixes` (open) — no overlap with this spec; relevant only to the #151 verdict.**

**Merged PR #394 (sandbox Tier-0) — makes the exit criteria cleaner, and changes nothing here.**

Workflow sessions are now sandbox-less by default (`warmSandboxOnClaim: false`), and a sandbox is provisioned lazily on the first filesystem tool. A seeded team workflow whose nodes are all tool and llm nodes therefore never provisions a sandbox, so credential resolution is the only thing that can fail on the path the dogfood below exercises. This narrows what the exit criteria prove, in this spec's favour.

## Testing

Unit and integration coverage lands with each task above. Five assertions carry the most signal, and they are spread across those suites.

A schedule-fired team workflow's tool node resolves a direct team credential. This is the exact path that fails today, and it is the one assertion that proves the whole of Half 1 hangs together.

A delegated reference follows through to a refreshed source token, and it breaks visibly rather than falling back when the delegator disconnects the service or leaves the team. The negative half matters as much as the positive half, because a silent fallback is the failure mode decision 3 exists to prevent.

A manual run and a scheduled run of one team workflow record the same owner, and the manual run additionally records the actor.

`createTeam` adopts one source per org workflow source atomically, and a team created in an org with no workflow source produces exactly the two rows it produces today.

`deleteTeam` reaps a team's workflows and their triggers, and refuses only while a run is unsettled.

Two suites cover the tenancy rules that a reviewer cannot check by reading a diff: `skill-source-credential.test.ts` for decision 14's bounded escalation, and `team-credential-store.test.ts` for the membership re-check on every reference follow. `make e2e` is the final gate for every task that touches a Docker-adjacent suite.

## Exit criteria (dogfood)

Run on a dev stack with the org Slack bot token stored at org scope and a GitHub App configured, and with a template repository registered as an enabled org-owned workflow source. That repository holds two workflows: a Slack digest on a schedule using `slack.send_message`, and a GitHub workflow whose tool nodes pin `credential: "app"`.

Create a team from the web. Its workflows list shows both, mirrored from the repository, within seconds of creation rather than at the next sweep. Fire the digest schedule and confirm that the bot posts the message and that the run is recorded as team-owned. Click Run on the same workflow and confirm that the run is recorded team-owned with your user as the actor. Push a commit that edits the digest's prompt, sync the team's source, and confirm the mirrored definition changes without a second workflow appearing.

Delegate a personal OAuth credential to the team from the integrations page, run a team workflow that uses that service, then have a second account with team admin remove you from the team. Confirm that the next run fails with the broken-reference error naming the fix, and that it does not silently use the triggering member's credential.

Finally, delete the team. Confirm that the mirrored workflows, their schedules, their subscriptions, and their webhooks are gone, that the adopted source row is gone, and that settled run rows survive.

## Non-goals

- The repository sync mechanism itself: the `.valet` dot-directory exception, the `workflows` folder discovery rules, the `origin` and `source_id` columns on `workflow_definitions`, the mirror reconcile, and the open-versus-org template distinction. All belong to `docs/specs/2026-08-24-workflows-mvp-design.md`.
- RBAC permission vocabulary. Routes keep `isTeamMember` and `canAdministerTeam`, for the reason given in the reconciliation section.
- Team-scoped OAuth connect, meaning the signed-state owner tuple in `credential-connect.ts`. Deferred per decision 9.
- Org-owned workflows, org orchestrator behavior, and org-scoped seeding.
- Seeding config-declared teams (`packages/api/src/services/config-reconcile.ts`) and identity-provider mirrors. Both are membership structures asserted at boot and at login by writers that must never throw, and neither is created through `POST /api/teams`.
- A delegated Slack identity for private-channel reads on team runs. Decision 8 locks fail-closed.
- Personal workflow sync. The 2026-08-24 call put it out of scope unless a GitHub repository backs it.
- Sandbox-facing route authorization on owner principals, a known limit tracked at `docs/specs/2026-08-17-team-workspace-ui-design.md:72-79`.
- New team-oriented template content. The workflows a template repository holds ship with `docs/specs/2026-08-24-business-workflows-design.md`.

## Open questions

1. **Should a team be able to opt out of an individual workflow the org's template repository publishes?** Recommended default: no in this pass. The org repository is the org's floor, and a per-team exclusion needs an `enabled` or suppression row that a mirror reconcile must then honor, which is mechanism the workflows MVP spec would have to carry. Revisit when a deployment asks. The escape hatch a team admin has today is to delete the adopted source, which removes the whole set rather than one item; `skill_sources.enabled` exists on the row but no route toggles it, so a per-source disable would be new surface too.

2. **When PR #163 lands, should a team-owner credential miss fall back to the org row for every service, matching the user-owner precedence that PR introduces?** Recommended default: no. Keep the narrow rule in decision 5, where only a `requires.orgCredential` service escalates. Symmetry with the user path is worth less than a team run failing for a nameable reason. Whichever pass lands second should record the decision in its Deviations section rather than let the two rules drift apart silently.

3. **When a delegator is removed from a team, should the reference row be deleted eagerly instead of failing at resolve time?** Recommended default: keep the resolve-time failure. The broken row is visible state an admin can act on by re-delegating or by storing a direct credential, while eager deletion would make the workflow's next failure look like a missing credential with no history.

4. **Should decision 12's tightening to `canAdministerTeam` apply retroactively to team skill sources that a plain member created before this change?** Recommended default: leave existing rows alone and apply the gate to new writes and deletes only. A retroactive sweep would need an owner to reassign the rows to, and the credential binding is already re-checked at read time, so an existing row is no more privileged than it was yesterday.

5. **Does the org's template repository need to be distinguishable from an org skills repository in the admin UI, or is the repository's content enough?** Recommended default: distinguish it. The workflows MVP spec owns the marker (decision 18's `listWorkflowSources`), and the sources list should label a row that carries workflow content, because decision 13 adopts only those rows into new teams and an admin needs to see which repository will reach every future team.

## Deviations from this design (recorded at implementation)

Recorded 2026-09-06. The design shipped as the stacked series PRs #572 to #591. `docs/specs/2026-07-21-team-resources-design.md` lands in the same commit as this section, restored from the `feat/rbac-permissions` branch, which is the only place the repository history held it. The entries below record where the shipped code differs from the decisions above, or where a decision left a case open that the code had to answer. Each entry names the decision, what shipped, and why.

1. **A team read that misses the team row can still reach an org-scoped 1Password item.** Decision 5 says a team-owned read stops at the team, except for a service that declares `requires.orgCredential`. What shipped keeps that rule for credential rows and adds one more source: when the team row is absent and the org-provided fallback does not apply, the resolver looks for an org-scoped 1Password item by service name, with scopes `["org"]`. There is no fallback to org credential rows for any other service. A 1Password item is placed in the org scope on purpose by an admin, so reaching it does not create the silent-borrowing trap that decision 3 closes. Product decision 2026-09-06.

2. **A team may store its own Slack bot token at team scope.** Decision 8 says a team-owned Slack run always uses the org bot token. What shipped lets a team admin store a Slack bot token under the team owner. The token is verified the same way as the org token: the bot token is checked and the required scopes are confirmed. The webhook signing secret is not required at team scope, because Slack events still route through the org app. Identity enrichment stays off for team owners, so private-channel reads still fail closed as decision 8 locks. Product decision 2026-09-06.

3. **The readiness predicate also gates the sync path, and it has a fourth ready condition.** Decision 15 defines `teamServiceReadiness` for the template install path. What shipped calls the same predicate from `content-sync/workflow-collector.ts` when a mirrored team workflow is armed, which replaces the blanket refusal in decision 9 of `docs/specs/2026-08-24-workflows-mvp-design.md`. The predicate gained a fourth ready condition: a service for which no plugin declares a credential is ready, because there is nothing for the team to hold. On the install path, membership is checked before readiness, so a non-member is refused before the predicate reads any credential row.

4. **The delete transaction commits before engine sessions are destroyed.** Decision 16 describes the reap as one transaction under the team ownership lock. What shipped orders the work in two steps. The transaction takes the lock, reaps the team-owned workflows, retires the team's assistants, and deletes the rows, then commits. Engine sessions are destroyed after the commit. The active-run check reads through the transaction handle instead of through the store, because a store read on a second connection deadlocked PGlite while the transaction held the lock. Product decision 2026-09-06.

5. **A manual run of an org-owned workflow stays owned by the caller.** Decision 7 says a manual run uses the definition owner on every path. What shipped applies decision 7 to team-owned and user-owned definitions only. A manual run of an org-owned workflow is stamped to the caller, so a plain org member cannot spend org credentials by clicking Run. Open for the tech lead: keep this rule, or gate org-owned manual runs to org admins and stamp the org as the run owner.

6. **A skills-only team source is still member-level on create.** Decision 12 requires `canAdministerTeam` for every create and delete of a team-owned source. What shipped requires `canAdministerTeam` on create only when the source collects workflows or templates, which follows decision 10 of `docs/specs/2026-08-24-workflows-mvp-design.md`. A skills-only team source stays member-level on create. Delete is admin-level for every kind. The two specs disagree on the create gate for a skills-only source. This entry records the disagreement; it does not resolve it.

7. **Decision 14 stands as written.** The adopted-source credential branch matches on `repo_full_name`, `ref`, and `subpath`. A provenance column that would have linked an adopted row to its org source was prototyped and dropped on 2026-09-06, because the address match already answers the question the column would have answered.

8. **A team run with no resolvable credential is refused before the action executes.** Decision 3 says resolution fails with a typed error when a reference is broken. What shipped also refuses a team run for a declared service when the team holds no credential at all, direct or delegated, before the action executes. The message names where to add one: team scope, a delegation, or the org fallback that applies to that service.

9. **The credential PUT reserves the delegation metadata keys on every scope.** Decision 2 describes a delegated reference as a team row that carries `metadata.delegatedFrom` and no secret, and decision 9 names the delegate route as the only writer of such a row. What shipped enforces that at the write boundary: `PUT /api/credentials/:service` refuses a body whose `metadata` carries `delegatedFrom` or `sourceType`, on the user, org, and team scopes alike, and the refusal names the delegate route. Without the check, a team admin could store a secretless team row that named any member, and the team read would follow it to that member's personal token. Recorded 2026-09-07.

10. **A `github` delegation is held to the user-row health rules.** Decision 9 lets any member share a service they have connected. What shipped applies the health predicate from `services/github-tokens.ts` (token present, not identity-only, not refresh-failed, fresh or refreshable) before a `github` row may be delegated, and the refusal names Connect GitHub in Settings → Connected accounts. The workflow invoker's team `github` branch applies the same predicate to a resolved delegated row, and falls through to the App installation path when the row fails it, the way it does for a team with no row. A row the member's own runs refuse would otherwise become a team credential every run rejects. Recorded 2026-09-07.

11. **A delegated source row cannot be re-stored as a personal 1Password reference, and the team list reports one as broken.** Decision 3 says a reference follows the delegator's live row and fails with a typed error when it cannot resolve. A team read runs with org-scoped 1Password tokens only, so a source row rewritten as a personal-scope reference is a reference that never resolves, and nothing said so until a run failed. What shipped closes both ends: the user-scope PUT refuses a personal-scope reference while any team holds a delegation of that service, and names revoking the shares or storing an org-scope reference as the fix; the team-scope GET marks a delegated row `referenceBroken` when the source row is a personal-scope reference, alongside the missing-source and lapsed-membership cases. Recorded 2026-09-07.

12. **The team-scope credential read admits an org admin off the team.** Decision 9 gates `GET /api/credentials?scope=team` on `isTeamMember`. What shipped gates it on `canViewTeam`: a member of the team, or an admin of the team's org. The write gate already admitted an org admin through `canAdministerTeam`, the team roster and the 1Password lease list already admitted one, and the Teams settings panel renders the credentials block for every team an org admin can see, so the member-only read returned 404 to the one person who could store the credential. `canViewTeam` now lives in `services/teams.ts` and both routes use it. A plain org member off the team still receives 404. Recorded 2026-09-07.

13. **Existing team sessions keep the acting-member resolution they were created with; new team sessions resolve as the team.** Decision 6 makes every team-owned session resolve credentials from the team principal. Before that decision shipped, a team-owned session resolved every service as the member prompting it, with the org fallback, and GitHub through that member's own row on `auto`. Applying decision 6 to those sessions would change what their tools can reach with no action by anyone, so `agent_sessions` gains a nullable `credential_owner_mode` column with the values `owner` and `actor`. The schema repair that adds the column stamps `actor` onto every team row present in the same transaction, once; every writer stamps a new row `owner`, and a later row with no mode reads as `owner` and is never rewritten. NULL reads as `owner`. For a team session in `actor` mode the host resolver, the GitHub branch, the prebuild-flag read, the Slack identity enrichment, and the OpenAI probe behave as they did before decision 6: the acting member's row, then the org fallback the service allows, with the team's 1Password scope. Everything else about the session, its principal for ownership and billing, its plugin filtering, and its team-key access, follows the merged design. The column is ignored for user- and org-owned rows. A child spawned by a team session in `actor` mode inherits `actor`, on its row and on its first build, so a conversation never switches identity between the orchestrator and the tasks it delegates. Product decision 2026-09-07.

14. **An interactive team session reads the team's own GitHub row before the App.** Decision 6 says the host resolver's `github` branch calls `resolveSessionGitHubToken` with `auth: "app"` for a non-user owner. What shipped for a workflow tool node (`plugins/action-invoker.ts`) reads the team's `github` row first, direct or delegated, and falls back to the App installation only when the team holds none. The host resolver now does the same for a team session in `owner` mode: it reads the team row through `resolveTeamCredentialRead` under the `github` fallback policy, skips a row that is identity-only or marked by a failed refresh (`isUsableGithubRow`, the same two health marks the user path applies), and otherwise proceeds to the App exactly as decision 6 describes. A team session and a team workflow now agree on which GitHub identity backs them. The prebuild-flag read stays on the App path. Product decision 2026-09-07.

15. **The OpenAI probe for a team session reads under the service's fallback policy.** Decision 6 routes every service other than GitHub and Slack through the owner read. The OpenAI probe (`services/openai-key.ts`) is its own path, because the org LLM-provider key comes first, and its team branch read the team row with no org fallback at all. A team workflow's openai node reads through the generic team resolver under `orgFallbackPolicy`, which for `openai` is `reference-only` and so reaches an org-scoped 1Password item by name (deviation 1). The probe now takes the same policy from the host, so a team session and a team workflow find the same org-scoped OpenAI item. The org credential row stays out of reach on both paths, because `openai` declares no org credential and the org LLM-provider key is the org-wide path for this service. Product decision 2026-09-07.

16. **The readiness predicate reads a team row the way a run reads it.** Decision 15 counts a team credential row as ready when the team holds one, and deviation 3 refined that to a row the run's decorator follows. What shipped goes through `resolveTeamCredentialRead` stopped at the team row, so the team's 1Password lease (`docs/specs/2026-09-04-team-onepassword-vaults-design.md`, decision 5) and the scope rule apply to readiness as they do on the run. A reference outside the lease is blocked with the refusal the run gives, and a reference in a deployment with no 1Password client is blocked naming the token to connect, where the row's presence alone used to arm a trigger that failed on every fire. The org-provided fallback and the by-name vault search stay separate conditions with their own reasons. Recorded 2026-09-07.

17. **An unpinned github node is ready through an App installation.** Decision 15 lists the App among the ready conditions only for a node that pins `credential: "app"`. The invoker's team branch (`plugins/action-invoker.ts`) serves an unpinned github node the same way after the team row misses: the installation for the node's `owner` parameter, or the org's sole installation. Readiness refused those nodes with the generic connect message, so a team template on a sole-installation org could not be installed. What shipped adds `installationResolvesFor` to `services/github-tokens.ts`, the same rule as `resolveInstallationApiToken` without a mint, and readiness treats an unpinned github node as ready when it holds for that node's literal `owner`. A templated owner is known only at fire time and is checked as absent. A `"user"` pin stays on the team row. An App that cannot pick an installation for the node is blocked with a reason naming the mismatch: the owner with no installation, or several installations and no owner parameter. No App, or an App with no installation recorded, keeps the plain connect reason, because the helper reads the installations table as it stands and does not run the lazy sync, which needs the App signing key a readiness caller does not hold. Recorded 2026-09-07.

18. **An adopted row collects workflows only.** Decision 13 copies `repo_full_name`, `ref`, and `subpath` from each org workflow source into the new team's row and says nothing about `kinds`. What shipped copied the org source's kinds verbatim, so an org source that collected skills and workflows together gave every new team a team-owned mirror of every org skill, and one that collected templates gave the team's gallery a second copy of every org template, each with its own poll of the repository. The adopted row now carries `kinds: ["workflows"]`. An org source that collects skills or templates already publishes them org-wide (`docs/specs/2026-08-24-workflows-mvp-design.md`, the template scope rule), so nothing a team could reach is lost. Recorded 2026-09-07.
