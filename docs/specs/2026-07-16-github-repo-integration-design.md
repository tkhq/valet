# GitHub / Repo Integration Design — App-first credentials, repo sessions, in-sandbox credential helper

**Date:** 2026-07-16
**Status:** Implemented
**Scope:** The v2 stack's GitHub and repository integration: a GitHub App-first credential model (self-serve App creation, org installations, short-lived installation tokens, user App-OAuth with refresh), repo-bound sessions (multi-repo, picker, clone-on-first-provision via a new engine prep seam), an in-sandbox git credential helper (no resident tokens), the token-resolution service all consumers share, and the settings surfaces for both. Supersedes the interim plan `docs/plans/2026-07-16-repo-sessions.md` (absorbed here). This is the foundation `2026-07-15-sandbox-images-v2-design.md` (prebuilds) builds on.

## Context

- **The v2 action surface already exists**: `packages/plugin-github` ships 28 actions + 12 trigger definitions reading a flat `"github"` credential via `ctx.credentials.get()`. What's missing is everything underneath: credential acquisition, repo-bound sessions, git in sandboxes.
- **v2 today**: sessions have no repo concept (no picker, no clone-at-start; sandboxes have `git` but are "repo-blind" — `mintSandboxEnv` injects no git/repo material). The only way to populate a `github` credential is manual PAT paste (`PUT /api/credentials/:service`) or the side effect of better-auth GitHub social login — whose token has default `read:user user:email` scopes (useless for repos), is saved create-only, and never captures `expiresAt`. There is **no refresh machinery anywhere in v2**: `StoredCredential.expiresAt` is written but never read. `/settings/connected-accounts` is Telegram-only.
- **Legacy (packages/worker) end-state** after three design iterations was GitHub App unified auth: manifest-flow App creation, `github_installations` table synced by webhooks, installation tokens minted per repo owner, App-based user OAuth. Two lessons learned the hard way, both avoided here: legacy grew **two inconsistent implementations** of credential resolution (`resolveRepoCredential` = user-OAuth-only, with the org-App fallback as a bespoke branch in `env-assembly.ts`) and **two installation-token minting paths** (cached and uncached). Legacy's generic `RepoProvider` interface only ever had GitHub implementations, and its shape was distorted by GitHub specifics (mintToken-as-passthrough).
- The credential store (`packages/api/src/plugins/credential-store.ts`) is a flat encrypted `(ownerType, ownerId, service)` KV — deliberately dumb; it stays that way.

## Decisions (locked)

1. **GitHub App-first.** One GitHub App per deployment, created self-serve via GitHub's manifest flow from admin settings (works on localhost — the manifest redirect round-trips through the browser). App credentials (`appId`, private key, OAuth client id/secret, webhook secret) are stored in the org credential store under service `github_app` (org-owned, encrypted) — never in env or config files. The manual PAT route survives as an escape hatch: a pasted user/org `github` PAT participates in resolution as a non-expiring OAuth token.

2. **Installations: on-demand discovery + optional webhook sync (both first-class).** New app-side table `github_installations`: `{ id, orgId, installationId, accountLogin, accountType, repositorySelection, suspended, linkedUserId?, createdAt, updatedAt }`. Populated by discovery (`GET /app/installations` with the App JWT) on setup, on "Refresh installations", and on settings-page open; when `VALET_PUBLIC_URL` is set, the App webhook endpoint (HMAC-verified, hardened-ingress shape like the Telegram webhook) keeps it live on `installation` events. Deployments without a public URL get the identical feature set minus real-time sync — the Telegram long-poll/webhook precedent.
   **Personal-account installations are first-class** (legacy parity, and the fork workflow depends on them): the App installs on user accounts exactly like orgs (`accountType: "User"`); discovery picks them up identically; resolution by `accountLogin` covers them with no special casing — a fork under `alice/` resolves `alice`'s personal installation for git pushes. `linkedUserId` is set when discovery can match the installation's account to a valet user's connected GitHub login (via their App-OAuth `/user` identity); it drives display ("your personal install") and the connected-accounts install affordance — resolution does NOT depend on it.

3. **One token service, one resolution function.** `resolveGitHubToken(deps, { orgId, userId, purpose, repo? })` in a single api service module is the ONLY implementation of credential resolution — every consumer (repos listing, clone prep, the sandbox credential-helper route, the 28 actions' `CredentialProvider`, later prebuild clones) goes through it:
   - `purpose: "git"` (clone/fetch/push/prebuild): installation token for `repo.owner` → user App-OAuth/PAT → **tokenless** (public repos clone bare; a private-repo failure surfaces git's own error plus a "connect GitHub or install the App on {owner}" hint). No token is ever required to bind a repo.
   - `purpose: "api"` (plugin actions): user App-OAuth/PAT → installation for the session's bound primary-repo owner → the org's sole installation when exactly one exists → clear error. The user→installation fallback is the **anonymous org-token path**: members with no personal GitHub connection get working GitHub actions through the org installation, attributed to the App bot (`{app}[bot]`). Not admin-gated; connecting a personal account upgrades attribution, not access.
   - Installation tokens are minted through ONE cached path (encrypted cache column on `github_installations`, 5-minute expiry margin). No second minting implementation, ever.
   - **Explicit credential selection beats precedence.** When more than one path could serve (e.g. the repo's owner has an installation AND the user is connected), the auto-precedence above is only the default: a repo binding may carry `auth: "auto" | "app" | "user"` (decision 5), and resolution honors an explicit choice STRICTLY — if the selected credential is unavailable/unhealthy, the operation fails with a clear error naming the missing credential; it never silently falls back across an explicit selection. `"app"` = installation token (bot-attributed commits/actions); `"user"` = the user's App-OAuth/PAT (user-attributed; pushes author AND commit as the user). API-purpose actions inside a repo-bound session follow the primary binding's `auth`; unbound sessions use auto-precedence.

4. **User App-OAuth + the refresh subsystem.** "Connect GitHub" (settings, distinct from sign-in) runs the App's user-OAuth authorize flow; callback saves `{ accessToken, refreshToken, expiresAt }` to the user-owned `github` credential. The token service treats `expiresAt - 5min` as stale and refreshes **single-flight** via the App's refresh endpoint, persisting the rotated pair atomically; refresh failure marks the credential unhealthy (surfaced in settings; resolution falls through per decision 3). Liveness logic lives entirely in the token service — the credential store stays dumb. The provisioning auto-save (social login) gets fixed en route: capture `expiresAt`; its create-only-hook limitation is documented, and its low-scope token is treated as connect-state "identity-only" in the UI (not repo-capable).

5. **Repo-bound sessions, multi-repo from day one.** New table `session_repos`: `{ sessionId, host, fullName, cloneUrl, ref?, auth, position }` (`auth` defaults `"auto"`, decision 3) — position 0 is the **primary** (drives default workspace naming and, later, prebuild resolution; secondaries always clone at prep). `CreateSessionRequest.repos?: RepoBinding[]` (with `repo?` sugar for one element); https clone URLs only. Workspace layout: single repo → `/workspace/<repoName>` is the repo root (today's ergonomics); multiple → side-by-side `/workspace/<name>` dirs. Unbound sessions are byte-identical to today. Mid-session binding additions are a non-goal this pass.

6. **Clone-on-first-provision via a new engine seam (adversarial review required).** `prepareSandbox?: (sandbox, epoch) => Promise<void>` on the session options object (the `resolveModel?` precedent): awaited inside the provision path after readiness, **before any waiter receives the sandbox** (the only race-free point); prep rejection fails the provision like a startup failure (no half-prepared handout); runs once per (sandbox, epoch) — re-provisions re-run it, hibernation wakes (same epoch) skip it. Absent hook = byte-identical. The api's prep implementation owns idempotence: `.git` exists → `fetch` + checkout (best-effort, offline-tolerant); else clone each binding sequentially. The engine seam knows nothing about git or GitHub.

7. **In-sandbox credentials: a dynamic credential helper, never resident tokens.** Prep installs a `valet-git-credential` helper and sets it as the sandbox's git `credential.helper`. On any git auth need it calls `POST /api/sandbox/git-credential` (authenticated by the existing `VALET_SANDBOX_TOKEN`), passing host+owner; the api resolves via decision 3 (`purpose: "git"`) **scoped to the union of the session's bound-repo owners** — a compromised sandbox cannot enumerate other installations — and returns a short-lived token the helper emits to git without writing to disk. Fresh token per operation: 1h installation expiry becomes irrelevant, wakes/restarts need no refresh choreography, the agent never sees a resident secret, and no `GIT_*`/`GH_TOKEN` env is ever injected. The clone in prep uses the same helper. `gh` CLI is baked into the sandbox images and wired to the same helper for git ops; `gh api`-style calls use a thin wrapper that fetches a token per invocation the same way. Git identity: `user.name`/`user.email` from the valet user profile set in the sandbox git config at prep.

8. **Generic where it's real, GitHub-specific where it isn't.** One thin api-side port:
   ```ts
   interface RepoHost {
     readonly id: string;                      // "github"
     listRepos(ctx): Promise<RepoListItem[]>;
     resolveGitToken(ctx, req: { owner: string; repo: string; purpose: "git" | "api" }): Promise<GitTokenResult | null>;
   }
   ```
   The repos route, clone prep, credential-helper route, and the actions' credential path consume the port, dispatched by clone-URL host. The App manifest flow, installations table, minting, and OAuth refresh are GitHub mechanics kept **private behind** the GitHub implementation — not abstracted (legacy's `RepoProvider` lesson). Data shapes (`session_repos.host`, `RepoListItem`) are provider-ready; a future GitLab implementation is a new `RepoHost`, no schema change.

9. **`GET /api/repos`** (any authed member): union of installation repos (per installed owner) + the user's App-OAuth repos, deduped by fullName, with `connected`/`installed` flags for picker hints; no credential and no installations → `{ repos: [], connected: false }` soft state (picker shows a connect hint). The session-create picker is optional typeahead single-select with an "add another repo" affordance; selection auto-fills the workspace path; no selection = today's flow. When BOTH an installation and a user connection could serve the selected repo, the picker shows an "Authenticate as" selector (Auto / App (bot) / Me) per binding — hidden when unambiguous.

10. **Settings surfaces.**
    - **Organization → GitHub (admin):** no App → "Create GitHub App" (manifest flow, org or personal target); with App → App card (name/id, "Install on GitHub" deep link, installations list with owner/selection/suspended, "Refresh installations", webhook status when public URL).
    - **Connected accounts (user):** GitHub row — Connect (App user-OAuth), connection state incl. token health (expired / refresh-failing / identity-only-scope badges), Disconnect (revoke + delete), and an "Install on your personal account" link (the App's install URL targeted at the user's account — enables the fork workflow; the resulting installation appears in the org's list flagged as personal/linked). Plus a generic credentials list from `GET /api/credentials` with revoke, making pasted PATs and other services visible/manageable at last.

## Exit criteria (the dogfood)

On a live deployment: create a real GitHub App via the manifest flow from admin settings; install it on an org; "Refresh installations" shows it (and with `VALET_PUBLIC_URL`, an uninstall shows up without refreshing). Pick a private org repo in the new-session dialog → session clones it on first prompt, agent runs a command in the repo, pushes a commit that lands bot-attributed with the user's name/email in the author field. Fork flow: install the App on a personal account, fork an org repo there (fork_repository action), bind the fork → clone + push resolve the personal installation. Connect a personal GitHub account → a plugin action (e.g. create_issue) attributes as the user; disconnect → same action still works via the installation (bot-attributed). Bind two repos to one session → both present side by side. Bind a public repo with zero credentials configured → clones fine. Token freshness: a session older than 1h keeps pushing (helper re-mints); a user token past 8h refreshes transparently on next API action. Sessions with no repo remain byte-identical to today.

## Testing

- **Resolution unit:** the full precedence matrix (both purposes × installation/user-OAuth/PAT/tokenless/none), owner-scoping of the helper route (unbound owner → org-level `auto` fallback; unrecognized host → 403 — see Deviations), sole-installation fallback, unhealthy-credential fallthrough; explicit `auth` selection is strict (selected-but-missing → clear error, never silent fallback; both directions).
- **Refresh:** stale detection at the 5-min margin, single-flight under concurrent reads, rotated refresh-token persistence, refresh-failure marking; installation-token cache re-mint at margin.
- **App flows:** manifest state signing/validation, setup-callback exchange (fixture GitHub), discovery sync upsert/removal, webhook HMAC + installation event handling, suspended installations excluded from resolution.
- **Prep/clone:** public tokenless clone, private clone via helper, multi-repo layout, `.git`-exists fetch path, prep failure → startup-failure semantics, unbound session byte-identical; token-discipline pins (no token in any exec argv, `git remote get-url origin` credential-less, no `GIT_*`/`GH_TOKEN` in sandbox env).
- **Engine seam:** `prepareSandbox?` ordering (before waiters), once-per-epoch, wake-skip, absent-hook byte-identical — adversarially reviewed like every engine touchpoint.
- **Fixture-first everywhere** (fake GitHub API on port 0); one live-gated e2e behind a real App credential set.

## Non-goals

- Webhook-**triggered** workflows (the App webhook ships for installation sync only; wiring plugin-github's 12 trigger definitions to it is a later pass).
- Non-GitHub hosts (the `RepoHost` port and provider-ready shapes are the extent of it this pass).
- Mid-session repo binding additions (agents can clone public repos themselves; private additions come later as a PATCH + on-demand prep).
- PAT deprecation; per-repo permission mirroring inside valet; org-level PAT sharing UI beyond what exists.
- gh CLI auth for arbitrary non-bound hosts; SSH clone URLs.
- Prebuilds (spec `2026-07-15-sandbox-images-v2-design.md` — builds directly on this foundation: build-time clones use decision 3's `purpose: "git"` with the config's repo owner, and `.valet/prebuild.yaml` reading rides the same clone).

## Deviations from this design (verified against commits ed8b8b9d..HEAD)

- **(2026-08-02) Credential shims install in EVERY isolated sandbox; unbound owners fall back to org-level resolution.** The original design 403'd any owner without a `session_repos` binding and only ran prep for repo-bound sessions — so orchestrator/unbound sandboxes had no helper at all and `gh` was never authenticated (the wrapper existed only as `valet-gh`, which no agent invoked). Three changes:
  1. The gh wrapper now ALSO installs as `/usr/local/bin/gh`, shadowing the image's binary on PATH. It locates the real `gh` by scanning PATH minus `/usr/local/bin`, and steps aside when the caller brings auth (`GH_TOKEN`/`GITHUB_TOKEN` set, or a `hosts.yml` from `gh auth login`).
  2. Sessions with no repo bindings get credential-only prep (`buildCredentialOnlyPrep`: helper + shim + git identity, no clones). Best-effort — failure logs, never a startup failure. Gated on the new `SandboxCapabilities.isolated` (docker/kubernetes only): local/virtual backends exec against the HOST, and prep would rewrite the developer's real `git config --global` and `/usr/local/bin`.
  3. `POST /api/sandbox/git-credential`: an owner with no binding (or no owner at all — the shim outside a repo) resolves through org-level `auto` (installation → user → org PAT → anonymous) instead of 403ing. This grants the sandbox nothing new: the same tiers back the session's own `github.*` plugin tools under the same user + org principal. A binding still resolves with ITS auth mode, including the strict 409 for explicit selections. New optional `purpose` body field (`"git"` default, `"api"` from the gh shim) picks the resolution ladder.
- **Credential-helper route auth header is `x-valet-sandbox`, not `Bearer`.** The route (`routes/sandbox-git-credential.ts`) is mounted on the existing sandbox-token rung of `middleware/auth.ts`'s ladder, which only reads `x-valet-sandbox` — there is no separate `Authorization: Bearer` path for it. The generated helper/`valet-gh` wrapper scripts send `x-valet-sandbox` accordingly.
- **Git protocol prerequisites, not optional prep steps.** `workspace-prep.ts` sets `credential.useHttpPath=true` (the credential helper derives `owner` from the request path, which git only sends with this flag) and `safe.directory '*'` (bind-mounted `/workspace` is owned by a different uid inside the container) unconditionally at prep — both are hard requirements for the helper to function at all, not tunables.
- **The org-owned PAT slot is shared with the user's App-OAuth connect credential.** Both write to the same `{type:"user"|"org", id}` / `github` credential-store key used everywhere else (decision 4's `PUT /api/credentials/:service` escape hatch and the App-OAuth connect flow are the same row) — a product decision to keep one canonical "the org/user's GitHub credential" slot rather than a second parallel PAT table. The connected-accounts UI shows a replace-warning before a PAT paste would overwrite a live App-OAuth connection (or vice versa).
- **Two engine seams landed, not one.** Decision 6 specified `prepareSandbox?`; a second seam, `credentialResolver?` (`CreateSessionOptions`, `engine/host.ts`'s `buildCredentialResolver`), was added when the session `call_tool` path (decision 3's `purpose: "api"` consumer) was found reading `github` credentials straight from the raw store instead of through `resolveGitHubToken` — the GH-T10 fix. Both are opus-reviewed byte-identical when absent (no `credentialResolver`/`prepareSandbox` key at all on an unresolved session's options).
- **Workflows and sessions reach `resolveGitHubToken` through two different wirings, not one uniform path.** Both ultimately call the same decision-3 resolution function, but: workflow tool-node invocations go through `workflows/engine-deps.ts`'s `invokeAction`, which has no session context at all, so a workflow run has no `session_repos` binding to read a repo or an `auth` mode from. Orchestrator and child sessions instead go through the `credentialResolver` seam (deviation above, GH-T10) attached to a real `EngineHost.sessionFor(...)` build, which DOES have session context and so DOES exercise the session-bound primary-binding branch when one exists. All three (orchestrator, child, workflow) resolve through the same token service instead of raw-store reads; only orchestrator/child land on a *binding-derived* resolution.
- **(2026-08-05) A workflow tool node selects its own credential, so workflows are no longer confined to `auto`.** Decision 3's explicit-selection rule (decision 5's `auth`) reached workflow runs only through a session binding, which a workflow run does not have — so a `github` tool node always resolved `auto` + `api`, whose first tier is the USER's own credential. Because every workflow definition is `ownerType: "user"`, an automated code review posted under that person's GitHub account whenever they had GitHub connected, and fell back to the bot only when they did not. `ToolNode.credential` (`@valet/workflow`, `"auto" | "app" | "user"`, optional) now rides the `WorkflowInvokeActionRequest` to `plugins/action-invoker.ts`, which calls `resolveSessionGitHubToken` with that `auth` and with the repo taken from the action's own `owner`/`repo` parameters. `"app"` mints the installation token for that owner or FAILS the node — decision 3's strictness, unchanged. Omitting the field keeps the previous precedence, so definitions written before the field exist behave identically. `resolveSessionGitHubToken` gained caller-supplied `auth`/`repo` overrides that outrank the binding; no second resolution path was added. A service other than `github` cannot select an identity: the invoker refuses the invocation rather than ignoring the selection and running as the workflow owner.
- **`hook_attributes` is always present in the manifest; only `active` toggles.** Manual-mode manifests (no `VALET_PUBLIC_URL`) still send `hook_attributes.url` pointed at `/webhooks/github-app` with `active: false`, rather than omitting the key — GitHub's manifest schema wants the key present either way, and this keeps a later `VALET_PUBLIC_URL` flip a pure `active` toggle instead of an add/remove.
- **Manifest-conversion failures are route-local status codes**, not a single generic error: GitHub rejecting the manifest code (bad/expired code) is `409`; GitHub's conversion endpoint 5xxing is `502`. Both are `POST /api/org/github-app/setup`-local, not part of the shared token-service error vocabulary.
- **`list_tools` probes survive a throwing `credentialResolver`.** A session with no `github` credential configured (`GitHubAuthError` on resolve) still lists the plugin's tools — `plugin-catalog.ts` turns a throwing resolve into a warning during discovery, not a hard failure; only an actual `call_tool` invocation surfaces the error to the agent.
- **`list_tools`'s per-service connected-probe now routes `github` through the `credentialResolver` (GH-T10), so a cold-cache tool listing can trigger a token mint/refresh.** `plugin-catalog.ts`'s discovery loop calls `ctx.credentials.get(service)` once per represented service to emit "no credential connected" warnings; for `github` that `.get` is the resolver, which may mint/refresh over the network. The cost is bounded by the token service's 5-minute mint cache + single-flight refresh (a warm cache re-listing pays nothing), so it is documented rather than engineered around in this wave. FOLLOW-UP (not built here — would add engine surface): the probe only needs "is `github` connected", which `CredentialProvider.list(owner)` (a raw store read, no mint) already answers; a dedicated cheap `has(service)`/`list`-backed probe seam in `plugin-catalog.ts` would remove the mint from discovery entirely.
- **Multi-repo workspace collisions land at `<owner>__<repo>`**, flat under `/workspace` (`workspace-prep.ts`), not a nested `/workspace/<owner>/<repo>` layout — kept as a single flat subdir so tooling that assumes `/workspace/<name>` (decision 5) only needs to handle one extra path segment, not arbitrary nesting depth.
- **Repo listing has undocumented-until-now caps**: `GET /api/repos` fetches `per_page=100` with no follow-up pagination for the installation/user-repos calls (`repos/github-host.ts`), while App-installation discovery itself (`services/github-app.ts`'s `fetchAllInstallations`) paginates up to a 10-page cap. An org/user with more repos or installations than that in a single source will not see the overflow — acceptable at today's scale per the module's own doc comment; revisit if it becomes a complaint.
- **RESOLVED (final-review fix wave): a session rebuild no longer revokes the token a running sandbox holds.** `mintSandboxToken` (`auth/sandbox-tokens.ts`) previously revoked all prior live tokens before minting; every cache-miss rebuild (`EngineHost.sessionFor`/`buildSession` → `mintSandboxEnv` — api process restart via `evictAll()`, orchestrator session PATCH via `evictCache()`) left the physical sandbox running while killing the token its in-container `valet-git-credential` helper / `valet-gh` wrapper were still reading from process env, 403ing every `POST /api/sandbox/git-credential` until pod recreation. Fix = candidate (1) verify-don't-revoke: a BUILD now mints an ADDITIONAL token without revoking live ones; the natural 24h TTL bounds how long a superseded token lingers. Explicit revocation stays only in `EngineHost.destroy()` (`revokeSandboxTokens`, cancels ALL of a session's tokens) — a stopped session's sandbox must lose its token.
- **(2026-08-14) `GITHUB_APP_*` environment fallback — a deployment can bring a pre-existing App through env, relaxing decision 1's "never in env".** Decision 1 stored App credentials only in the org credential store, and the manifest flow was the only intake — it always CREATES a new App, so a deployment with an existing App (or one that lost its DB) had no way in. `loadAppConfig` (`services/github-app.ts`) now falls back to `resolveGithubAppEnvConfig` when the org has no `github_app` credential row. The env vars: `GITHUB_APP_ID`, `GITHUB_APP_SLUG`, `GITHUB_APP_CLIENT_ID`, `GITHUB_APP_CLIENT_SECRET`, `GITHUB_APP_PRIVATE_KEY` (PEM, raw or base64), and optional `GITHUB_APP_WEBHOOK_SECRET`. Properties, all deliberate:
  1. **The env is the config — nothing is written to the DB.** Rotation = rotate the env + restart the api. A partial variable set throws (names the missing vars) instead of silently acting unconfigured.
  2. **A credential row shadows the fallback.** An org that later completes the manifest flow uses its own App; `GET /api/org/github-app` reports `source: "org" | "environment"` so admins can tell which is live. `DELETE` removes only the row + installation rows; it cannot remove env config (the response stays `configured: true, source: "environment"` until the operator unsets the vars).
  3. **The fallback is deployment-wide**: with no row anywhere, EVERY org resolves the same App — same single-App/single-org posture as `findGithubAppOrgId`'s documented caveat, now reachable from first boot.
  4. **Webhook deliveries verify against the env webhook secret** when no `github_app` row exists, then route by the payload's `installation.id` to the org that synced that installation, else to the deployment's oldest org (`resolveEnvFallbackOrgId`, `routes/github-app.ts`).
  5. **Prerequisite the code cannot check:** the pre-existing App's webhook URL must point at `{public URL}/webhooks/github-app`, and its callback URL at `{public URL}/api/me/github/callback`, or webhooks/user-connect silently go elsewhere.
  The helm chart carries the values: non-secret half under `api.githubApp.*` (ConfigMap), secret half under `api.secrets.githubApp*` (Secret) — see `deploy/chart/valet/values.yaml` and the chart README. The `VALET_GITHUB_LIVE_*` vars remain e2e-test fixtures, unrelated to this fallback.
- **(2026-08-14) `github:installation` virtual credential service — `list_repos` switches the CREDENTIAL with its `scope`, not only the endpoint.** `github.list_repos` with `scope: "installation"` (and the documented `auto` 403-fallback) previously reused the one credential `getOctokit` resolved up front. When the user had a linked user token, that token won `auto` + `api` resolution, and `GET /installation/repositories` rejects user tokens outright ("Resource not accessible by integration") — so the installation listing failed for exactly the users who were fully set up. The plugin now requests `ctx.credentials.get("github:installation")` for the installation listing. Both credential seams answer it via `resolveInstallationApiToken` (`services/github-tokens.ts`): the session resolver (`engine/host.ts`) prefers the primary binding's owner, then the org's sole non-suspended installation; the workflow invoker (`plugins/action-invoker.ts`) prefers the action's own `owner` parameter. `null` (no App installation) leaves the plugin on its previous single-credential behavior, and its 403 error then names the corrective step. The service name is a literal in both the api and the plugin — the plugin cannot import from `@valet/api` (dependency direction).
- **(2026-08-17) The App's own webhook URL is asserted at boot and after setup, but only for an App this instance owns.** Decision 1 fixes the webhook URL when the App is created. An instance behind an ephemeral tunnel therefore runs with a dead delivery URL — a `cloudflared` quick tunnel gets a new hostname on every restart — and inbound events stop with no error on either side. `syncAppWebhookUrl` (`services/github-app.ts`) reads `GET /app/hook/config`, and writes the current URL with `PATCH /app/hook/config` only when the two are different. Both calls use the App JWT, the same credential `discoverInstallations` uses. `main.ts` calls `syncAllAppWebhookUrls` once at boot, for every org that owns a `github_app` credential row. `GET /api/org/github-app/setup` calls it for the org it just configured, because the URL in the manifest can already be stale when GitHub redirects back. Four properties hold this safe:
  1. **`source === "org"` is the whole guard.** Only an App whose credential lives in THIS instance's database is synced. An App from `GITHUB_APP_*` came from a deployment, or from a dev App a team shares, so a different instance owns it. Syncing it would point the team's webhooks at whichever developer booted last, and each subsequent boot would take them back. This is also why item 5 above stays a prerequisite the code cannot check.
  2. **Idempotent.** The read comes first, and the write occurs only on a difference. A boot that changes nothing sends no write.
  3. **It never clears.** With no public URL, it does nothing and logs at debug level. A deployment can set the hook URL deliberately, and an empty URL stops delivery for everyone.
  4. **Fail-soft.** It runs at boot and inside the setup callback, so a GitHub outage, a revoked key, or a 4xx is logged and swallowed. The boot call is not awaited: two GitHub round trips must not delay the listening port.
- **Known open issue (pre-existing auth-v2 lifetime gap, out of this arc): the 24h `VALET_SANDBOX_TOKEN` TTL strands sandboxes older than a day.** With rebuild-revocation removed, a token now expires only by its 24h TTL — a sandbox that stays running past that (no rebuild re-mints, since rebuild pushes the new token into a fresh env only on `restore()`, never into an already-running container) will 403 its credential helper once the token it holds expires. This is the same non-refresh-into-a-live-container gap the auth-v2 sandbox-token lifetime already has, not new to this arc; flagging so the eventual push-on-rebuild / in-container token refresh work covers it.
