Valet has two kinds of integration: **Action Integrations** and **Channel Integrations**.

- **Action Integrations** are the ones this page covers — the tools your orchestrator can *call* on your behalf. Every entry in the catalog below is an Action Integration.
- **Channel Integrations** are Slack and Telegram — bi-directional channels that let you *talk to* Valet from those apps, with Valet replying in the same place. See [Channel Integrations](/product/integrations/channel-integrations) for the full story.

Some plugins are both. Slack is the key example: it's an Action Integration (with actions like `slack.send_message` and `slack.read_history`) **and** a Channel Integration (you can DM Valet in Slack and it'll answer you there). The same connection powers both. Telegram is channel-only.

## Action Integrations

Valet ships first-class integrations as plugins under `packages/plugin-*`. Each Action Integration contributes one or more actions an agent can call, an optional trigger source for inbound events, and a provider definition that controls how credentials are stored.

Two action-shape flavors are in use today:

- **Inline action plugins** — actions are defined in Valet's own source with explicit names, parameters, and risk levels. The pages below list every action and its params.
- **MCP-proxied plugins** — actions are forwarded to a remote [Model Context Protocol](https://modelcontextprotocol.io) server. The plugin owns auth and the default risk level; the upstream MCP server owns the live action catalog. Agents can enumerate the live actions with `list_tools`.

All actions, regardless of shape, are subject to the same [approvals](/product/approvals) and [policy](/engineering/policy-engine) layers.
